Still open on 1.26.06-40. The output is byte-identical to the report:

```
i1 : R = QQ[x];

i2 : peek'_3 factor (1 * (x-1) * (x-2)^2)
o2 = Product{Power{R{x-2}, 2}, Power{R{x-1}, 1}}

i3 : peek'_3 factor (2 * (x-1) * (x-2)^2)
o3 = Product{Power{R{x-2}, 2}, Power{R{x-1}, 1}, Power{R{2}, 1}}
```

Four separate asks accumulated in this thread, and none of them has been acted on:

1. **The constant factor is absent when it is 1**, so a program cannot rely on its presence
   (`o2` vs `o3` above).
2. **Exponents of 1 are always shown**, so the human-oriented output is noisier than it needs
   to be.
3. **The constant comes last rather than first.** @pzinn noted he had moved it to the front
   in an experimental branch "with no discernible issue", and @DanGrayson replied "I must
   have had a reason for doing it that way at the time!" — so the original reason is no
   longer known to either of them.
4. **The constant is not in the coefficient ring.** Still true: in `o3` the factor `2` is
   `Power{R{2}, 1}`, an element of `R = QQ[x]`, not of `QQ`. @pzinn agreed this one should
   change.

Two further data points from today, since neither is in the thread:

```
i4 : S = ZZ[y];

i5 : peek'_3 factor (6 * (y-1))
o5 = Product{Power{S{y-1}, 1}, Power{S{6}, 1}}

i6 : peek'_3 factor (1_R)
o6 = Product{}
```

The unit case degenerates to an empty `Product` — worth knowing for anyone writing the
uniform-output option @DanGrayson proposed, since it is another shape a consumer has to
handle.

That proposal is the concrete piece of work here:

> We should provide an optional argument for returning something uniform for programs, and
> also, in the human oriented case, omit the exponents that are equal to 1.

Recording the state rather than reopening the design discussion — the thread already reached
agreement on what should happen, and nothing has changed since 2017.
