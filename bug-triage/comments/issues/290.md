**Re-scoping this issue, and retitling it to match.** The bug reported here was fixed in
2015–2017 — by forbidding the input rather than by fixing the computation — so what remains
open is the capability that was removed, not the defect. The old title described a symptom
nobody will see again.

### What happens now

```
i1 : R = ZZ[x_1..x_3, Weights => {-1, 2, -1}, Global=>false];

i2 : gens gb ideal(1+x_1, 2*x_1)
Core/gb.m2:160:28:(1):[17]: error: Groebner bases in rings over ZZ with variables
                                   less than zero are not yet supported
```

No non-idempotent Gröbner basis, because there is no Gröbner basis: the computation is
refused. The same is true of the `RevLex` variant in #291, which fails at the same line with
the same message.

### How that happened

The chain is short and it starts with this report.

- **5 June 2015** — @jakobkroeker files this and #291, two orderings of the same test.
- **6 June 2015** — @mikestillman files #294, *"Logic for deciding if a GB algorithm applies
  is incomplete"*, specifying precisely this guard: *"If the base ring is ZZ (ultimately),
  then the only allowed algorithm is 'Inhomogeneous'. If the monomial order is a local
  order... then the algorithm must be 'Inhomogeneous'. **BUT: if both of these hold, then a
  'not implemented yet' error should be given.**"*
- **8 June 2015** — #294 closed completed, front-end checks in place.
- **31 May 2017** — [`e552ee18be`](https://github.com/Macaulay2/M2/commit/e552ee18be),
  *"disallow for now: local gb over ZZ"*, adds the engine-side guard these two now hit.

So the wrong answer was not corrected; the input that produced it was made illegal, which is
what #294 asked for and is a reasonable resolution of a correctness bug.

### What this issue tracks from here

The capability that removal took away, which as far as I can tell **nothing else tracks**.
Searching every issue body and all 16,874 issue comments for a local monomial order together
with ZZ and Gröbner bases turns up only #294 (closed, the guard's own specification), and
#1985 — which is `Global => false` over `QQ`, a different ring and a different problem.

Two things say the gap is understood rather than settled. #294: *"the GB routine itself can
handle it, but my minimalization algorithm isn't designed for that case (yet)"*. And the
commit message: *"disallow **for now**"*.

Retitled and retyped from Bug to Feature accordingly. #291 is being closed as fixed and
points here, since its `RevLex` case was verified to hit the same guard and adds nothing this
issue does not already carry.
