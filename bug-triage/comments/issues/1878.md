Closing this as a duplicate of #1548, which @pzinn proposed here in 2023 and confirmed again in
June. The behaviour is unchanged — on 1.26.06-40-gd8e86d689d, @mahrud's table still comes out
exactly as reported:

```m2
last func(1:a,Foo=>bar) -- 1:a
last func(1:a)          --   a
last func(1:1:a)        --   a
last func(1:1:1:a)      -- 1:a
last func(1:1:1:a,F=>b) -- 1:1:1:a
```

The shared mechanism is `override`. `M2/Macaulay2/m2/option.m2:35` carries a TODO citing *this*
issue, and it sits directly above the `>>` implementation whose body is
`uncurry(f, override (,args))` — so the option-stripping described here happens inside the function
#1548 is about. @DanGrayson's summary above, that "having the system process options for our
function is an idea in conflict with the idea of having the system present our arguments to us
unchanged", is the same statement from the other end.

Two things worth carrying across rather than losing:

  `override` is for internal use, it would be good also to see how the problem occurs at top level,
  when defining and calling a method function with options. Can you provide an example?" The
