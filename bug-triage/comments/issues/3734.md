Closing as not-a-bug, with two working invocations, since the answer here turns out to be an
explanation rather than a change.

**The `random` half is fixed and @Devlin-Mallory's diagnosis was right.** The code he quoted is gone;
`genmat.m2:115-119` now returns `homomorphism random(Hom(G, F, DegreeLimit => 0), opts)` when the
source is not free, which descends by construction rather than hoping a random map of the covers
does. That was #3828. `isWellDefined random(M, M)` is now true in 40 of 40 trials over `QQ`, and over
`CC` as well.

**The remaining failure is not in `inducedMap`.** Over `CC`:

```
inducedMap(M, M)             -> ok
inducedMap(M, image gens M)  -> ok
inducedMap(M, ker r)         -> error
```

with the `QQ` version of the last one succeeding. The cause is floating point: `gens(ker r) %
relations M` is not zero, but its largest entries are of order `1e-16` —

```
matrix {{(3.71399e-16+1.05207e-16*ii)*y, -1.6464e-16*ii*y}, ...}
```

— so the containment holds to machine precision while the test is exact. Specifically it is the
check at `matrix.m2:703`, `if not isWellDefined f'`, that fires; none of the `% relations`
comparisons above it is involved. M2 warns about this on the way in: *"experimental computation over
inexact field begun — results not reliable."*

Two ways to get the map over `CC`:

```m2
inducedMap(M, ker r, Verify => false)
inducedMap(M, image clean(1e-10, gens ker r))
```

The first leaves the module alone and skips a check that cannot succeed over an inexact field. The
second keeps the check meaningful at the cost of choosing an epsilon, and it is the same submodule —
the cleaned module and the kernel contain each other to within `1e-10`, with the same number of
generators.

An approximate well-definedness test over inexact fields, or an error message that names the
exactness mismatch rather than just saying the map is not well defined, would be a reasonable
feature request and a separate issue.
