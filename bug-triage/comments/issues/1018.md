Fixed — but not by changing the regexp, which is still byte-for-byte the line quoted above. It
now lives at [`m2/run.m2:26`](https://github.com/Macaulay2/M2/blob/development/M2/Macaulay2/m2/run.m2#L26).
What changed is the other side of the match.

### The chain

The bracket the regexp requires is printed conditionally:

```
-- d/stdiop.d:135
if recursionDepth > 0 then stdError << "[" << recursionDepth << "]:";
```

and `recursionDepth` is incremented only when an M2 closure is applied (`d/actors3.d:1775`).
Package tests are fed to `M2` on standard input (`run.m2` uses `readmode(SetInputFile, "<" | inf)`),
so they are evaluated at the top level — and in 2019 the top level was entered like this:

```m2
interpreter := commandInterpreter
```

a direct alias to the compiled built-in. Calling it applies no closure, so `recursionDepth` stayed
`0`, no bracket was printed, the regexp could not match, and `aftermatch` returned nothing — which
is exactly the missing error line reported here.

[#4145](https://github.com/Macaulay2/M2/pull/4145) *"Allow abortions"* (@mahrud, merged
2026-02-25) replaced that alias with a closure:

```m2
interpreter := () -> (
    loadDepth = errorDepth = 3;
    n := commandInterpreter();
    ...)
```

Applying it raises `recursionDepth` to 1, so `[1]` is now printed and the regexp matches.
`recursionDepth()` at the top level returns `1` today, and every stdin error carries the bracket —
checked on an assertion failure, a division by zero, an explicit `error`, and a syntax error.

Current behaviour, on a package with two failing tests:

```
 -- error log:  /tmp/M2-719854-0/0.tmp:0:1:(3):[16]: stdio:3:6:(3):[1]: error: assertion failed
 -- input code: ErrorPkg.m2:19:5-21:3
```

### @mahrud — your 2020 question, answered

It was **not** fixed at that point; it had five more years to run. The check in that comment —
*"I tried `check("ErrorPackage")`, but it worked correctly (i.e., the check failed)"* — confirms
that `check` **detected** the failing test, which was never in doubt. The report here is that it
did not **display** the underlying error. Those are different, and the second one was still broken
in 2020.

### The coupling is still there

Nothing ties these two ends together except the value of `recursionDepth` when a top-level error is
printed. If the top level ever returns to depth `0` — another rearrangement of how
`commandInterpreter` is entered would do it — the bracket stops being printed, this regexp silently
stops matching, and `check` goes quiet about test errors again with no other symptom. Making the
bracket optional in the pattern, as @jkyang92 suggested in the second comment above
(`(\[[0-9]+\]:)?`), would remove the dependency.
