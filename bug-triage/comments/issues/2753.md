Answering this after a long silence: the code is unchanged, but it is not doing what it looks like,
and binary exponentiation would be slower. Closing on that basis, with one loose end noted below.

The segment linked above is still there byte for byte — only the file moved, to
`e/rings/poly.cpp`. What it implements is not repeated multiplication. `PolyRing::power_direct`
splits `f = lead + rest` and expands by the binomial theorem, accumulating `rest^i` incrementally;
and in positive characteristic `PolyRing::power` writes `n` in base `p` and applies Frobenius to
coefficients and monomials, added by @rz10x in 4449069c33 (2019) and already in place when this was
filed.

Both of those beat binary exponentiation, for two different reasons.

*Large times small, rather than large times large.* Binary exponentiation reaches `f^32` by squaring,
and the last squaring squares the 153-term `f^16` — about 153² term products, most colliding and
needing to be merged. The binomial expansion instead multiplies a growing polynomial by `rest`, here
just `y+z`. Roughly `N^2` against `n*N*t`, for `N` the size of the answer and `t` of the input.

*Base `p` collapses where base 2 does not.* `(x+y+z)^81` over `ZZ/3` is `x^81+y^81+z^81`. Writing 81
in base 3 and applying Frobenius keeps three terms throughout. Binary exponentiation passes through
`f^64`, which has C(66,2) = 2145 terms and none of the collapse, so squaring it is millions of term
products.

Measured on 1.26.06 against a hand-coded binary exponentiation, asserting equal results each time —
ratios are binary-exp time over engine time:

```
(x+y+z)^32           QQ           183x
(x^10+y^10+z^10)^20  QQ            32x
(a_1+..+a_8)^6       QQ            15x
(x+y+z)^32           ZZ/32003      83x
(x+y+z)^81           ZZ/3        8200x     (13 microseconds, 3 terms)
(2x+3y)^40           QQ             7x
```

Being straight about the last line: with a one-term tail the cost model slightly favours binary
exponentiation, so that 7x is almost certainly overhead in my harness, which drives the
multiplications from the interpreter, rather than a real advantage.

The one part of the original concern that survives is "lots of copies", which I have not measured.
There are three concrete constant-factor costs per iteration of the loop: `mult(g, rest)` and
`mult_by_term(g, coef3, m)` are two full-length allocations where the scaling could plausibly be
fused into `add_to`; and `K_->power(lead->coeff, n - i)` and `M_->power(lead->monom, n - i, m)` are
both recomputed from scratch on every pass, where an incremental update would do. None of that
changes the asymptotics or the conclusion above, but it is a real optimization opportunity — worth a
fresh issue if anyone wants to take it, rather than keeping this one open.
