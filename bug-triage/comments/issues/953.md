Closing as `wontfix` — the defect is real, but fixing it would be speculative, and the tool it is
in is the larger question.

The mechanism, for the record. `Macaulay2/html-check-links/lex.l:27` declares three exclusive
start conditions and `script` is not among them:

```
%x string tag comment
```

So `<script>` is an ordinary tag: the rule on line 45 returns the lexer to `INITIAL` at its `>`,
and everything through `</script>` is scanned as markup. Anything in the JavaScript shaped like a
link is looked up as one:

```html
<script>
document.write("<a href='ghost.html'>generated</a>");
</script>
```

```
script.html:4:25: error: broken link: ghost.html
```

The same page with the `<script>` block deleted exits 0.

It is bounded in two ways. A bare `<` is survivable — `for (var i = 0; i < 10; i++)` opens a tag,
but `{WORD}` on line 40 excludes `>`, so the tag closes at the `>` in `</script>` and scanning
resumes in the right state; a broken link *after* such a script is still reported. And nothing we
ship triggers it: across the 11870 installed HTML pages of a 1.26.06 build there are exactly three
distinct inline `<script>` bodies — the KaTeX macro table `defaultHEAD` puts on every page
(`m2/html.m2:15`), `macros["\\Hom"] = "\\operatorname{Hom}"` on three pages (Complexes,
SimplicialModules, MatrixFactorizations), and `macros["\\OO"]` on one (Text). None contains a `<`.
Everything else is `<script src=...>`, whose `src` is a real file and should be checked.

So `make check` passes on account of what the JavaScript happens to contain rather than anything
the checker does — but no page has hit it in the seven years since this was filed, and a start
condition added now would be fixing a fault nothing has run into.

The question this really raises is whether `html-check-links` should still exist. It is a
hand-written flex and bison program in `Macaulay2/html-check-links/`, wired into `make check` and
into `test_build.yml`, and general-purpose HTML link checkers have been packaged and maintained
for years now. I have not surveyed them properly, so this is one data point rather than a
recommendation: [LinkChecker](https://linkchecker.github.io/linkchecker/) gets this issue's case
right in both directions, without needing to be told about `<script>` at all:

```
$ linkchecker --no-warnings script.html          # the page above
That's it. 2 links in 2 URLs checked. 0 warnings found. 0 errors found.

$ linkchecker --no-warnings broken.html          # a real broken link, no <script>
Result     Error: URLError: <urlopen error [Errno 2] No such file or directory: '.../ghost.html'>
That's it. 2 links in 2 URLs checked. 0 warnings found. 1 error found.
```

and it handles the installed tree as it stands: `linkchecker --recursion-level=1
Text/html/index.html` under `share/doc/Macaulay2` checks 89 links with no errors, resolving the
relative `../../../../Macaulay2/Style/katex/...` script sources correctly. It is also packaged in
Debian — stable, testing and unstable, on every release architecture — and in Ubuntu, which is
what a build dependency would need. (`lychee` and `htmltest` are the other names that come up;
neither is in Debian or Ubuntu, so both would be a harder sell here.)

That does not settle anything. This program may well be doing things a general-purpose checker is
not, `--no-absolute-links` among them, and somebody would have to go and look. But it does mean
the real choice here is between teaching this lexer about `<script>` and asking a much broader
question — and the broader question deserves its own issue rather than being carried by this one.

Reopening is right if a package does start emitting markup inside an inline script: the symptom
will be `make check` failing with a broken-link error pointing at a line that has no link on it.
