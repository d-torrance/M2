Fixed. Autotools guards on `.git` now, and the guard is in the one place that needed it.

`M2/autogen.sh` only touches the submodule when M2-emacs is actually missing, and only when there
is a repository to fetch it from:

```sh
if test ! -f $srcdir/Macaulay2/editors/emacs/M2.el
then
    if test -e $srcdir/../.git
    then
	echo "-- Updating M2-emacs submodule"
	git submodule update --init $srcdir/Macaulay2/editors/emacs
    else
	echo "-- Warning: Not in a git repository; unable to update M2-emacs submodule."
	echo "-- You may download it from https://github.com/Macaulay2/M2-emacs and extract"
	echo "-- its contents to the Macaulay2/M2/emacs subdirectory."
    fi
fi
```

That arrived with `4d0415ebf0`, *"Replace Makefile with autogen.sh shell script"*, in
[#3520](https://github.com/Macaulay2/M2/pull/3520). A build from a `git archive` tarball — which is
how the Debian source package is made, and the case that prompted this issue — now gets a warning
telling it where to download M2-emacs, instead of a failing `git submodule update`.

No other submodule is touched by the autotools build unless the corresponding library is actually
being built. The only remaining `git submodule` line in `M2/Makefile.in` is at line 148, inside the
`$(DIST_NAME).tar.gz` target, which needs a repository by its nature.

For the record, `cmake` had reached the same place from the other direction —
`cmake/build-libraries.cmake:119` reads `if(GIT_FOUND AND EXISTS "${CMAKE_SOURCE_DIR}/../.git")` —
which is what @mahrud was pointing at above.
