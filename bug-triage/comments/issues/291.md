Closing as fixed. The reported behaviour is gone, and it went the same way as its sibling
#290 — the input was made illegal rather than the computation corrected.

Verified on 1.26.06-40:

```
i1 : R = ZZ[x_1..x_3, MonomialOrder=>{RevLex}, Global =>false];

i2 : gens gb ideal(-2+3*x_1^3, -1+2*x_1^2)
Core/gb.m2:160:28:(1):[17]: error: Groebner bases in rings over ZZ with variables
                                   less than zero are not yet supported
```

There is no longer a Gröbner basis whose re-computation could disagree with itself, because
`gb` refuses the ring. The `Weights => {-1,2,-1}` case in #290 fails at the same line with
the same message, so both orderings are covered by one guard.

That guard is deliberate. @mikestillman filed #294 the day after these two were reported,
specifying it — *"if both of these hold, then a 'not implemented yet' error should be
given"* — and #294 closed completed on 8 June 2015 for the front-end checks;
[`e552ee18be`](https://github.com/Macaulay2/M2/commit/e552ee18be) (2017, *"disallow for now:
local gb over ZZ"*) added the engine-side check that fires above.

**#290 stays open and has been re-scoped to track what the guard took away** — local
Gröbner bases over ZZ being unsupported rather than merely unreliable — since nothing else
in the tracker does. Closing this one rather than #290 keeps the older record, and this
issue's `RevLex` ordering is noted there as independently verified.

If a local Gröbner basis over ZZ ever misbehaves again in a way the guard does not catch,
that would be new and worth its own report.
