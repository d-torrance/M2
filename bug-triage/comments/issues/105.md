Notes from a sweep of the open issues. Short version: **the inhomogeneous answer appears to
be correct, the documentation promises less than the code delivers, and the `Strategy`
option is documented in a way that does not match what `mingens` does with it.** Checked on
1.26.06-40.

### The behaviour looks right, which is not what the request assumed

The request reads as though silence might be covering a wrong answer. As far as it can be
tested, it is not:

- 300 randomly generated inhomogeneous ideals in `QQ[x,y,z]`: in every case no single
  generator of the returned set could be dropped and still generate.
- Deliberately redundant families all collapse correctly — `(f, g, x*f + y*g)` gives two
  generators, and `((x-1), (x-1)*(y-2), (x-1)*z)` gives one.
- The documentation's own example, `I = ideal(a-1,b-2,c-3)^2`, goes from 9 given
  generators to 6, and 6 is the true minimum: translating the point to the origin makes
  the ideal `(a,b,c)^2`, where `trim` also gives 6.

### But the documented guarantee is much weaker than that

[`mingens-doc.m2`](https://github.com/Macaulay2/M2/blob/development/M2/Macaulay2/packages/Macaulay2Doc/functions/mingens-doc.m2)
already says, under `(mingens, Ideal)`:

> If I is not homogeneous, then an attempt is made to find a more efficient generating
> matrix, one which is better than a Gröbner basis. There is no guarantee that the
> generating set is small, or that no subset also generates. **The only thing known is that
> the entries do generate the ideal.**

That is honest, and it is the real answer to this issue: the *guarantee* is absent for a
mathematical reason, not the correctness. Over a graded ring, or over a local ring, minimal
generators are well defined up to isomorphism by Nakayama. For a general inhomogeneous
ideal in a polynomial ring there is no such statement to appeal to, so the algorithm cannot
certify minimality even in the cases where it has achieved it. What trips people up is
reading `numgens mingens I` as an invariant; it is not one, and the documentation says so
in a place people evidently do not reach.

### Why an error is probably the wrong remedy

Two concrete obstacles, both measurable.

**It would break real code, mostly through `trim`.** `trim` calls `mingens` six times in
[`m2/matrix2.m2`](https://github.com/Macaulay2/M2/blob/development/M2/Macaulay2/m2/matrix2.m2),
so an error in one is an error in the other. Hooking `(mingens, Module)` and running four
package test suites to completion gives:

| suite | homogeneous | inhomogeneous |
| --- | ---: | ---: |
| IntegralClosure | 2135 | 454 |
| LocalRings | +636 | +5 |
| NumericalSemigroups | +61 | 0 |
| HyperplaneArrangements | +171 | +1 |
| **total** | **3003** | **460** |

13% of all `mingens` calls are on inhomogeneous input, and `IntegralClosure` alone accounts
for 454 of them. All four suites pass today.

**`isHomogeneous` is the wrong test in any case.** The documentation's own framing is
graded *or local*, and over a local ring the module is not homogeneous while `mingens` is
entirely legitimate:

```m2
i1 : needsPackage "LocalRings";

i2 : R = QQ[x,y]; P = ideal(x,y); RP = localRing(R, P);

i3 : N = ideal(promote(x^2+x, RP), promote(y, RP));

i4 : isHomogeneous module N

o4 = false

i5 : mingens module N

o5 = | x2+x y |
```

A guard on `not isHomogeneous` alone would reject exactly the case the documentation
blesses.

### Separately: the `Strategy` option does not behave as documented

Found while checking the above, and not tracked anywhere I could find. The same doc page
says:

> The standard (default) strategy for `mingens` or `trim` is `Complement`, at least in the
> case where the module (or ideal) is homogeneous, and the ring is (quotient ring of) a
> polynomial ring over a field. The other strategy, `Inhomogeneous`, is experimental.

Three things about that, for `mingens`:

1. **The switch is automatic, and not driven by the option.** `matrix2.m2:197` defaults
   `Strategy` to `Complement` unconditionally, and the fast path is then guarded by
   `opts.Strategy === Complement and isHomogeneous M and isAffineRing ring M`. Inhomogeneous
   input fails that guard on its own, whatever was passed. The "at least in the case where"
   hedge gestures at this without stating it.

2. **`Strategy => Inhomogeneous` is inert for `mingens`.** `mingens` compares `Strategy`
   against `Complement` and nothing else; `Inhomogeneous` is a real branch only in `trim`,
   at `matrix2.m2:245` and `:275`. So the sentence quoted above sits on the `mingens` page
   describing something only `trim` does.

3. **`mingens` accepts an unrecognized `Strategy` silently, where `trim` refuses it:**

```m2
i2 : I = (ideal(a-1,b-2,c-3))^2;

i3 : mingens(I, Strategy => Complement) == mingens(I, Strategy => Inhomogeneous)

o3 = true

i4 : mingens(I, Strategy => symbol Nonsense);

             1      6
o4 : Matrix R  <-- R

i5 : trim(I, Strategy => symbol Nonsense);
stdio:5:4:(3):[1]: error: trim: unrecognized Strategy option
```

There is a `-- TODO: the strategies should be separated` at `matrix2.m2:193` that looks
like it is about this.

### Suggestion

Recast as documentation and signature work rather than a behaviour change: say on the
`mingens` page that the inhomogeneous path is selected automatically by homogeneity rather
than by `Strategy`, that `numgens mingens I` is not an invariant for inhomogeneous `I` and
why, that `Inhomogeneous` applies to `trim`, and make `mingens` validate `Strategy` the way
`trim` does. The original question in this issue — how much existing code would break — now
has a number attached to it above, and it is large enough to be the answer on its own.
