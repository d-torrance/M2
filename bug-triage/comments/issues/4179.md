On the disagreement about `https://` — you are both right, and which one you see depends on the
server.

`https://` is implemented by shelling out to `openssl s_client -quiet -verify 1 -host H -port 443`
([`http.m2:45-52`](https://github.com/Macaulay2/M2/blob/033342d15dac9405f315f8ea212337b73a3fcb9d/M2/Macaulay2/m2/http.m2#L45-L52)).
For `google.com` the TLS verification succeeds and the response arrives in full — and then `openssl`
exits 1 anyway:

```console
$ printf 'GET / HTTP/1.1\r\nHost: google.com\r\nConnection: close\r\n\r\n' \
    | openssl s_client -quiet -verify 1 -host google.com -port 443
depth=2 C = US, O = Google Trust Services LLC, CN = GTS Root R4
verify return:1
depth=1 C = US, O = Google Trust Services, CN = WE2
verify return:1
depth=0 CN = *.google.com
verify return:1
HTTP/1.1 301 Moved Permanently
Location: https://www.google.com/
[... the rest of the headers and body ...]
80707E871B7E0000:error:0A000126:SSL routines:ssl3_read_n:unexpected eof while reading:../ssl/record/rec_layer_s3.c:316:
$ echo $?
1
```

`google.com` drops the connection without a TLS `close_notify`, which OpenSSL 3 reports as
`unexpected eof while reading`, and M2's `close` turns that exit status into `code 256`. `oeis.org`
and `macaulay2.com` do send `close_notify` and exit 0 — hence the URL that worked for @pzinn.

It is not a certificate-depth problem: both chains are depth 2, and `-verify 2` and `-verify 3` fail
the same way. `-ign_eof` does not help either. So the response is fetched successfully and then
discarded on teardown.

That 301 is also item 1 in miniature. A non-200 comes back as ordinary content, with no error:

```m2
i2 : #getWWW "http://macaulay2.com/"

o2 = 1178

i3 : first separate("\r\n", getWWW "http://macaulay2.com/")

o3 = HTTP/1.1 301 Moved Permanently
```

And on item 3, an unsupported scheme is not an error today — the protocol table has only `http://`
and `https://`, and the surrounding `select(1, protocols, ...)` leaves the result at its initial
`""`, so you get an empty string rather than a complaint:

```m2
i4 : getWWW "file:///etc/hostname"

o4 =
```

`ftp://` behaves the same way. Whatever is decided about supporting `file://`, that silent `""` looks
worth fixing on its own.
