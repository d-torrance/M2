Closing as obsolete, from a sweep of the open issues — the reporter's problem was solved on
this thread in 2017, and the environment it happened in is long gone.

Both questions asked here were answered at the time. @DanGrayson gave the way to continue
past example errors,

```
make IgnoreExampleErrors=true
```

and @catselbow found the actual cause and reported back:

> Thanks for the tip about "IgnoreExampleErrors", but I did eventually get it to build by
> fiddling with the memory limits. [...] A fresh build with an 8GB limit worked.

So this was a virtual-memory limit on the build host, not a defect in M2, and it was resolved
nine years ago. The context — M2 1.10 on CentOS 6.8, a distribution that reached end of life
in November 2020 — no longer exists, and the build system has been reworked substantially
since.

### The one thing left, and why it needs a fresh issue rather than this one

@DanGrayson's closing remark still stands on its own merits:

> I regularly build M2 in a 1.6 GB virtual machine, so it's unreasonable for 3GB to be
> insufficient.

That is a fair concern, but it was never turned into anything specific, and a 2017 memory
figure from a dead distribution is not something anyone can act on today — current build
requirements are a different question with different numbers. If the build footprint is a
problem now, that deserves its own issue with a current measurement, current toolchain and
current configure flags, rather than inheriting this thread.

Worth noting for anyone who lands here from a search: `gdbm` is still in `LIBLIST` in
`configure.ac`, so the component that produced `gdbm fatal: couldn't init cache` is still
part of the build. If that message reappears, a new issue with the build log and the ulimit
settings would be more useful than reopening this one.

Thanks @catselbow for following up with what actually fixed it — that is the part that made
this thread worth reading.
