Closing this, because `roots` is a thin wrapper and the numerics are not Macaulay2's.

`roots` calls `rawRoots`, which is `e/interface/polyroots.cpp` — 168 lines that include
`<mps/mps.h>`, marshal the coefficients into an MPSolve problem, and marshal the roots back out.
Every decision about accuracy is MPSolve's. So if there is a bug here it is upstream, and this
tracker is not where it would be fixed.

For what it is worth, I could not produce an inaccurate root by any means I tried, using
polynomials built from roots known in advance:

| | worst error |
| --- | --- |
| `(x-1)^4`, `(x-1)^8`, `(x-1)^12` | 3e-48, 9e-44, 2e-42 |
| roots at `1` and `1 + 1e-8` | 2.2e-16 |
| roots of magnitude 1e-3 up to 1e3 | 1.1e-13 |
| degree 19, exactly representable roots, magnitudes 0.06 to 16 | 1.6e-14 |
| `(x-1)(x-2)...(x-19)` | exact |

Repeated roots are the standard way to break a root finder, and recovering a 12-fold root to 1e-42
indicates MPSolve is working well past double precision internally.

### Why the test above cannot see what it is looking for

The measurement is `sub(f, x => maxRoot)`, an absolute residual at the largest root of a degree-19
polynomial. At that scale the individual terms of `f` are enormous and must cancel, so the residual
is set by the size of the terms rather than by the quality of the root. The clearest demonstration
uses no root finder at all — take `f = (x-1)(x-2)...(x-19)`, whose roots are exactly the integers
1 to 19, and evaluate at one of them:

```m2
i1 : R = RR[x];  f = 1_R;  scan(1..19, k -> f = f * (x - k));

i2 : sub(f, x => 19.0)

o2 = -80314900000
```

`19` is a perfect root, and it evaluates to -8e10, because the largest term of `f` at `x = 19` is
about 2.4e41 and a double carries ~16 significant digits. A threshold of `1e-2` is fifteen orders
of magnitude below the noise floor of the measurement itself.
