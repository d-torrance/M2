Closing as not planned, from a sweep of the open issues — not because the request was
answered, but because nine years on the situation it protects against has barely arisen.

### The scenario needs `throw` to be in use, and it is not

The case @DanGrayson eventually granted here is a real one:

> if the code containing "throw" is also getting used correctly by code containing "catch",
> then it can be hard to locate the code not containing "throw" that calls it incorrectly,
> unless a backtrace is available.

That requires packages to use `throw`/`catch` as control flow. Across the whole package
tree today, essentially one does — `DirectSummands.m2`, at four call sites:

```m2
if isSurjective c then throw (c, rightInverse c)              -- :538
if isIsomorphism(c * b) then throw (c, b)                     -- :548, :555, :560
```

Every other match is prose: comments like "otherwise, throw error", documentation saying a
method "will throw an error", and `HardDegreeLimit => {}  -- throw out information in
degrees above this one`. Core uses `throw` once.

So the cost @DanGrayson objected to — *"it would slow down Macaulay2 to save backtrace
information for every throw just in case"* — is constant and real, and the benefit is very
nearly hypothetical.

### On `stacktrace`

@mahrud's 2020 note is adjacent to the request rather than an answer to it. `stacktrace`
takes an integer and has two modes, neither of which is an automatic backtrace at an
uncaught throw:

- `stacktrace 0` prints a **C++** trace via Boost::stacktrace — `evaluate_evalraw`,
  `readeval3`, engine frames with `.dd` line numbers. Useful for debugging the interpreter,
  not for finding the M2 code that called something wrongly.
- `stacktrace n` for `n > 0` returns a sequence of positions from `M2_stack`, the profiler's
  top-level call log, and
  [`d/profiler.dd:26`](https://github.com/Macaulay2/M2/blob/development/M2/Macaulay2/d/profiler.dd#L26)
  still carries `-- TODO: limit this to Code, packages, stc for traceDepth = 1, 2, 3, etc.`,
  so the depth argument is not really implemented.

Both are things you call deliberately, at a point you have already identified — which is the
opposite of the situation this issue is about.

### If it is ever wanted

@jakobkroeker's last suggestion here was never answered and is still the obvious shape:
opt-in collection, disabled by default. That answers the performance objection directly,
since nothing is saved unless somebody asks for it. It is recorded here so that whoever
needs it does not have to rediscover it — and if `throw`/`catch` ever becomes a common
idiom in packages, this should be reopened rather than refiled.

Closing on lack of demand, not on the merits. Thanks for the careful argument at the time,
@jakobkroeker — the use case you identified was granted, it simply has not materialised.
