@mahrud asked in July 2024 what the issue is here. It still reproduces on 1.26.06-40, and
this is the shape of it:

```
i1 : R = QQ[x,y];

i2 : g = matrix{{x,y}};

i3 : f = matrix{{x^2}};

i4 : f % g == 0

o4 = true

i5 : f // g

o5 = {1} | x |
     {1} | 0 |

             2      1
o5 : Matrix R  <-- R

i6 : f // gb g

o6 = 0

                   1
o6 : Matrix 0 <-- R
```

`f` is in the image of `g` — line 4 says so — and `f // g` produces the witness. Passing the
Gröbner basis explicitly instead produces a zero map, of the wrong shape, with no
indication that anything went wrong. Asking for the change matrix restores the right
answer:

```
i7 : f // gb(g, ChangeMatrix => true)

o7 = {1} | x |
     {1} | 0 |
```

So the difference is entirely the `ChangeMatrix` option, whose default is `false`, and the
failure mode is a silently wrong value rather than an error — which is what the opening
report says.

On @mikestillman's 2017 note that this might be desirable behaviour: that reading is
easier to defend for the *shape* than for the *value*. Returning a map out of `R^0` is at
least a visible signal that no change matrix was available. Returning it as the answer to
`f // gb g` when `f` genuinely is in the image is a wrong answer to a question that has a
right one, and nothing in the session distinguishes it from the case where `f` really is
not in the image.

Worth noting that the two-argument form `f // g` computes what it needs and gets it right,
so the trap only springs when a caller has computed a Gröbner basis for some other purpose
and reuses it here — which is exactly when it is least likely to be noticed.
