Two things measured on 1.26.06-40-gd8e86d689d before closing, because the thread left both open.

### The mechanism is intact

One documentation database per loaded package, held open:

```
baseline                            29 open descriptors, 24 of them documentation .db
after needsPackage on 40 packages   62 open descriptors, 57 of them documentation .db
```

Roughly one per package, so about 300 at the current 299 packages. (Approximate — some of
those 40 were already loaded at startup, and I did not load all 299.)

### But the scenario in the report no longer happens

The issue opens with *"loading them all, just to see what's in them, as is done to generate a
list of all the packages with their headlines for the documentation."* That no longer loads
anything. Both package-wide lists in `Macaulay2Doc/ov_packages.m2` use `readPackage` — the
headline list at line 19 and the author list at line 49 — which is what #1085 asked for, and it
is closed. `m2/help.m2:407` does the same for package headlines in `help`.

The other candidate, `checkAllPackages` (`m2/testing.m2:140`), does iterate every package, but
through `runString` → `runFile`, which spawns a **separate process** per package, so it never
accumulates descriptors either.

I could not find anything in the tree that now loads every package into one session, so the
exposure is a user doing it by hand. Worth adding that the 256 limit cited above is the macOS
default; `ulimit -n` on the Linux box used here is 1048576, so the headroom is very
platform-dependent.

None of that makes the design in #1643 less worth doing — it removes the per-package descriptor
entirely — but it does mean nothing is currently falling over, which seemed worth recording
before this thread stops being the place people look.
