The feature asked for here exists — `ker` takes `DegreeLimit` and it is documented at
`[kernel, DegreeLimit]`. **Leaving this open anyway, and retitling**, because on the example
in this issue the option silently returns the wrong thing, and that turns out to be a
general property rather than a quirk of the example. The original title, "kernel should
allow degree limits", describes the part that is done.

### It works exactly as documented — when the map is homogeneous

Grading `R` so that this issue's own map is degree-preserving:

```m2
S  = ZZ/32003[s,t];
Rg = ZZ/32003[a..d, Degrees => {4,4,4,4}];
phi = map(S, Rg, {s^4, s^3*t, s*t^3, t^4});
```

```
isHomogeneous phi                       true
kernel generator degrees                {8, 12, 12, 12}

ker(phi, DegreeLimit => 4)              ideal()
ker(phi, DegreeLimit => 8)              ideal(b*c-a*d)
ker(phi, DegreeLimit => 12)             ideal(b*c-a*d, c^3-b*d^2, a*c^2-b^2*d, b^3-a^2*c)
ker(phi, DegreeLimit => 16)             (same)
```

Precisely the documented behaviour: *"stop after generators for the degree `d` part of the
kernel have been discovered."*

### The example in this issue is not homogeneous, and there it misleads

With the default grading — which is what the issue writes — `a` has degree 1 and maps to
`s^4`, so `isHomogeneous phi` is **false**. Then:

```
kernel generator degrees                {2, 3, 3, 3}

ker(phi, DegreeLimit => 2)              ideal()
ker(phi, DegreeLimit => 3)              ideal()     <-- the line in this issue
ker(phi, DegreeLimit => 4)              ideal()
ker(phi, DegreeLimit => 5)              ideal()
ker(phi, DegreeLimit => 10)             all four generators
```

So `ker(phi, DegreeLimit=>3)` — the exact expression written in the report — returns the
empty ideal, for a kernel whose generators sit in degrees 2 and 3. Nothing warns, and
`ideal()` is indistinguishable from "the kernel really is trivial through degree 3".

### Why

`kernel RingMap` builds the graph ideal and hands the options straight to `gb`
([`m2/ringmap.m2`](https://github.com/Macaulay2/M2/blob/development/M2/Macaulay2/m2/ringmap.m2)):

```m2
graph := generators graphIdeal f;
G := gb(graph, opts);
ideal mapback selectInSubring(1, generators G)
```

`DegreeLimit` therefore bounds the Gröbner basis computation *on the graph ideal*, not the
degrees of the kernel generators that come out of `selectInSubring`. When the map is
homogeneous the graph ideal is homogeneous too and the two coincide, which is why the graded
version above behaves perfectly. When it is not, the degrees the computation works through
have no simple relation to the degrees of the result — hence 5 giving nothing and 10 giving
everything for generators of degree 2 and 3.

### What would settle it

Either a homogeneity guard — refuse or warn when `DegreeLimit` is given for a map that is
not homogeneous, since the number cannot mean what the documentation says it means — or a
caveat on `[kernel, DegreeLimit]` stating that the limit applies to the underlying Gröbner
basis computation and is only interpretable in the kernel's own grading when the map is
homogeneous. The first is preferable: a silent empty ideal is the failure mode this issue
happens to demonstrate, and it is not one a caller can detect.

Related in shape and in code: #4618, *"graphIdeal and graphRing accept MonomialOrder and
silently ignore it"*. Different option and a different location — that one is a fault in
`graphIdeal` itself, this one is `ker` misapplying a good `graphIdeal` — but both are options
accepted on the graph-ideal path that do not do what the caller would reasonably expect.
