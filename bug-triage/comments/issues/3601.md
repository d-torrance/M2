Still reproduces on 1.26.06, and the diagnosis above is half of it — there are **two** defects in one
expression, `gfanInterface.m2:756-757`:

```m2
  R2 := (coefficientRing R1) new Array from (for i in 1..#R1Gens list (
    value ("x" | demark ("",for i from 1 to numDigits-(length toString i) list "0") | toString i)
  ) );
```

The variable names are built as strings and resolved with `value`, so if the caller has a global
`x1`, the new ring is built on **the caller's symbol** — before `use` is reached. Then
`(coefficientRing R1) new Array from (...)` is `Ring Array`, which is where the `use R monoid M`
above comes in, rebinding those globals to the new ring. Fixing only the second leaves a package
that still builds its rings out of whatever symbols happen to be defined.

The fix is this file's own idiom elsewhere: `getSymbol` is already used at `:1709`, `:1803`, `:1810`
and `:2333`, and it avoids both problems.

On the user-side question, @felixlotter's own last comment is the answer — `QQ[local x, local y]`
gives the scoping he was after, with the caveat in his EDIT that `use foo(1)` still leaks the
symbols. Worth separating the two: a package should not need `local` to avoid clobbering its caller,
which is what the lines above are about; whether `use` on a returned ring ought to be containable is
a different and larger question.
