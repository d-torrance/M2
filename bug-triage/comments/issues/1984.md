Worth flagging that the guard added in #4361 is present in the build joel-dodge's run above failed on,
so the exception is escaping by some other route.

`1fcecd4c5f` wraps all of `RingElement`'s arithmetic — unary minus, `+`, `-`, `*`, `*(int)`, `/`,
`power(int)` and `power(mpz_srcptr)` — in `try`/`catch` on `exc::engine_error`, which is what the
diagnosis above asked for. But that macOS job built `259d30c7ee`, and

```
git merge-base --is-ancestor 1fcecd4c5f 259d30c7ee    # succeeds
```

so the guard was compiled in, and the log still ends:

```
-- capturing check(2, "SuperLinearAlgebra") libc++abi: terminating due to uncaught exception of
type exc::overflow_exception: monomial exponent overflow: pos int32_t + pos int32_t
```

So the diagnosis was wrong about *where* the exception gets out, rather than the fix being wrong.
`Monoid::mult` is reached from plenty of places that never go through `RingElement`'s operators —
`schreyer-orders.cpp`, `gbring.cpp`, `res-a0-poly.cpp`, `Eschreyer.cpp` — and the 2022-02-10 backtrace
in this thread arrives at `Monoid::Monoid` via `IM2_Monoid_make`, which is monoid construction, not
element arithmetic. Whatever path this test takes, it is not one of the eight now guarded.

The two package-level causes in that diagnosis are also untouched, and they are the cheaper way to stop
this particular test crashing:

- `SuperLinearAlgebra.m2:50` still builds a weight vector of length `2n` for an `n`-variable ring, so
  the `Weights` block is truncated to its leading `n` entries, which are all zeros. The intended
  weights are discarded and the order is effectively plain `Lex`.
- `check(2)` and `check(3)` still build `T1` and `T2` over `R` rather than over `QQ`, which is what
  produces the ring with duplicated ordering blocks.

One caveat when comparing results: the Debian and PPA builds of this package carry three
`-- no-check-flag #1984` markers, so a passing `check "SuperLinearAlgebra"` from a distribution build
is not evidence either way.
