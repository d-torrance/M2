Closing: this is a Flint bug, not an M2 one, and it has been fixed upstream.

The stack trace #3523 added puts the abort inside libflint rather than in factory. Reproduced on
1.26.06, frames trimmed:

```
Flint exception (General error):
    lenP < 2 in n_poly_mod_invmod
 6# n_bpoly_mod_factor_lgprime in /lib/x86_64-linux-gnu/libflint.so.18
 9# nmod_mpoly_factor_irred in /lib/x86_64-linux-gnu/libflint.so.18
11# factorize(CanonicalForm const&, bool) in /lib/x86_64-linux-gnu/libsingular-factory-4.3.2.so
13# rawFactorBase(...) at interface/factory.cpp:711
```

So factory hands Flint the polynomial and Flint aborts inside `n_bpoly_mod_factor_lgprime`.

That function was repaired by [flintlib/flint#2612](https://github.com/flintlib/flint/pull/2612),
*"Fix three bugs in the more: branch of lgprime bivariate factoring"*, merged 2026-03-18, fixing
their [#2611](https://github.com/flintlib/flint/issues/2611). The first of the three is this
symptom: *"next_alpha_pow was multiplied by itself instead of curr_alpha_pow, producing zero on
first entry … This caused a crash in `n_bpoly_mod_make_monic_mod` when trying to invert modulo
zero"* — and inverting modulo zero is what `lenP < 2 in n_poly_mod_invmod` reports.

Checked rather than assumed: running Flint's own reproducer from their #2611 — Fredrik Johansson's
degree-18 trivariate form over `GF(3)`, from a Sage report — through `factor` here gives the
identical message in the identical frame. Same bug.

The first Flint release containing the fix is **v3.5.0** (2026-04-24). M2 does not vendor Flint —
`configure.ac` requires only ≥ 2.6.3 — so whether a given build crashes depends on the Flint it
links:

| Flint | crashes? |
| --- | --- |
| Debian sid / forky, 3.6.0 | no |
| Debian trixie, 3.1.3 · bookworm, 2.9.0 | yes |
| Ubuntu 24.04, 3.0.1 (measured above) | yes |

@mikestillman's "still crashes in development build on 26 April, 2025" predates the upstream fix by
eleven months, so it isn't evidence against this.
