Both halves still reproduce on 1.26.06, byte for byte — the `freeResolution` pair gives `key not
found in hash table: isComputable` and `{Complex, Nothing}`, and five scheduled `syz gens M`
gives `-- SIGSEGV handler called a second time, aborting`. (The path in your transcript was
`FreeResolutions.m2:91`; the file is now `FreeResolution.m2`, same line, same error.)

For the first half the window is four lines wide, and it is a publish-before-initialize.
`freeResolution Module` builds the resolution object with five keys and publishes it
immediately:

```m2
    RO = new ResolutionObject from {
        symbol ring => ring M,
        symbol LengthLimit => opts.LengthLimit,
        symbol DegreeLimit => opts.DegreeLimit,
        symbol Strategy => opts.Strategy,
        symbol Module => M
        };
    M.cache.ResolutionObject = RO;          -- line 113

    C = runHooks((freeResolution, Module), (opts, M), Strategy => opts.Strategy);   -- line 116
```

`isComputable` is not among those five keys. It is installed by the strategy hooks that
`runHooks` invokes on line 116 — `RO.isComputable = ...` appears at lines 188, 404, 426, 488 and
550, one per strategy. So between line 113 and line 116 there is a resolution object visible in
`M.cache` that has no `isComputable`.

A second thread calling `freeResolution` on the same module during that window reaches

```m2
    if M.cache.?ResolutionObject then (            -- line 86: true, A published it
        RO := M.cache.ResolutionObject;            -- line 87
        ...
            if RO.isComputable(opts.LengthLimit, opts.DegreeLimit)    -- line 91: not there yet
```

which is exactly the reported error, and it explains why the failing task returns `Nothing`
while the other returns a `Complex`: one thread completes normally, the other dies on a key the
first has not written yet.

Two things this does **not** cover, so as not to imply one fix handles everything here:

- The `syz` SIGSEGV is a separate failure. It is in the engine rather than in this script, and
  nothing above bears on it.
- Publishing `RO` after `runHooks` instead of before would close this particular window, but
  `M.cache` is being read and written by both threads throughout, so that is an observation
  about where the reported error comes from rather than a proposed patch.
