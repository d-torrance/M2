Closing: both of these exist now.

> a way to lock global variables before accessing them

The `Mutex` type with `(lock, Mutex)` and `(unlock, Mutex)`, added in `e1723bd865` on 2025-04-18,
backed by pthread mutexes in `d/pthread.d`.

> ideally also a way to indicate that a given piece of code may not be run in parallel with itself
> (e.g. something silly like `capture = threadlock capture`)

`(lock, Function)`, added in #4378 on 2026-05-27 and re-implemented in `df999fbf2c` using the `with`
keyword. It is `threads.m2:32-33`, built on the mutex primitives. That PR's own demonstration is the
clearest statement of it: `parallelApply(1..1000, f)` on a counter-incrementing `f` leaves the counter
at 345, and `parallelApply(1..1000, lock f)` leaves it at 1000.

And the case this issue opens with is fixed by the same mechanism: ring creation was the first thing
`lock` was applied to, the culprit being `makeMonomialOrdering`, which now reads

```m2
makeMonomialOrdering = lock((monsize,inverses,nvars,degs,weights,ordering) -> (
```

at `engine.m2:190`. So "creating a ring is not reentrant, so if you try to make a ring many times in
parallel eventually things get garbled" no longer holds.

Core is not thread-safe throughout — the documentation machinery and `capture` are still unguarded —
but that is a broader subject than this issue, which asked for the two facilities above.
