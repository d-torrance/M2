Notes for whoever updates the documentation. **No change in behaviour is being proposed
here** — `decompose Ideal` has computed minimal primes for the whole of M2's recorded
history, a great deal of code depends on it, and after this long that is the right place
to leave it. What follows is the history of the name and the alternatives a reader might
have in mind, gathered while triaging the open issues, so it can be cross-referenced
rather than rediscovered.

### The name has been walked back twice, in the direction this issue asks for

The behaviour for `Ideal` has never changed. The *naming* has, twice, and both times
towards less synonymy:

| when | commit | what happened |
| --- | --- | --- |
| 1997–2006 | — | `decompose` is the **primary** name: `decompose = method()`, `decompose Ideal := ...`. `minimalPrimes` exists only for `MonomialIdeal`. |
| 2006-07-03 | [`119f3cdd`](https://github.com/Macaulay2/M2/commit/119f3cdda8e723cbd2b876e97e6e4b3ccf1f06bc) | *"changed decompose to minimalPrimes"* — `minimalPrimes Ideal` becomes the implementation and `decompose` is demoted to a literal symbol alias, `"decompose" => symbol minimalPrimes` in `m2/exports.m2`. From here they are the *same object*. |
| 2008-11-12 | [`661998a0`](https://github.com/Macaulay2/M2/commit/661998a02b) | *"make prune and decompose not total synonyms of minimalPresentation and minimalPrimes, respectively"* — the aliasing is removed and they become two method functions sharing one implementation. Announced in [`changes, 1.2`](https://github.com/Macaulay2/M2/blob/development/M2/Macaulay2/packages/Macaulay2Doc/changes.m2). |
| 2019-07-26 | [`092cdd50`](https://github.com/Macaulay2/M2/commit/092cdd50c2) | `MinimalPrimes` becomes the default provider; `decompose = method(Options => true)` in core. |
| 2020, 2024 | — | hookified and moved out of core. |

Worth knowing when reading this thread: the 2008 commit deletes a file from the old
`bugs/` tree named `bugs/dan/0-confusing-synonyms`, whose entire contents were

> these synonyms are perhaps not so good:
>
> ```
> "decompose" => symbol minimalPrimes,
> "prune" => symbol minimalPresentation,
> ```

so the objection in this issue had already been raised, and partly acted on, six years
before it was filed. (That file was deleted in 2008 and so is not among the 857 removed
by `d2c8d27826` and catalogued in #36.)

### What `decompose Ideal` computes, stated exactly

`intersect decompose I` is `radical I`, not `I`. The two agree precisely when `I` is
radical. Where they differ, `decompose` can return **fewer components than the ideal has
associated primes**, because an embedded prime is not a minimal one:

```
i3 : J = ideal(a^2, a*b)

             2
o3 = ideal (a , a*b)

i4 : decompose J

o4 = {ideal a}

i5 : primaryDecomposition J

                          2
o5 = {ideal a, ideal (b, a )}

i6 : associatedPrimes J

o6 = {ideal a, ideal (b, a)}

i7 : intersect decompose J == J

o7 = false

i8 : intersect decompose J == radical J

o8 = true
```

This is the strongest form of the objection in the original report, and it is sharper
than what was written there: the complaint is not only that the pieces do not reassemble,
it is that a component can be absent from the list altogether.

None of that makes the current behaviour wrong. In algebraic geometry "decompose" most
often does mean the irreducible components of the variety, which is exactly what minimal
primes give, and `MinimalPrimes/doc.m2` already says so — "Geometrically, it decomposes
the algebraic set defined by `I`". The point is only that the identity and its limits are
not stated anywhere a reader will find them.

### Other things "decompose an ideal" can reasonably mean

All of these already exist in M2 under their own names; the documentation could point at
them from `decompose`:

| what a reader might want | M2 | reassembles to |
| --- | --- | --- |
| irreducible components of `V(I)` | `decompose` / `minimalPrimes` | `radical I` |
| the classical primary decomposition | `primaryDecomposition` | `I` |
| intersection of irreducible ideals | `irreducibleDecomposition` (`MonomialIdeal`) | `I` |
| all associated primes, embedded included | `associatedPrimes` | — |
| the unmixed, top-dimensional part | `topComponents` | — |
| components over the algebraic closure | `numericalIrreducibleDecomposition`, and `decompose WitnessSet` | — |

### Two shipped documents that disagree

- [`Macaulay2Doc/shared.m2`](https://github.com/Macaulay2/M2/blob/development/M2/Macaulay2/packages/Macaulay2Doc/shared.m2) documents `decompose` as a general verb: *"decompose an object … a method function, defined in the core so multiple packages can add methods to it."* That reading is supported by the other three methods — `BettiTally`, `WitnessSet` and `MultiprojectiveVariety` — each of which does decompose its argument.
- [`MinimalPrimes/doc.m2`](https://github.com/Macaulay2/M2/blob/development/M2/Macaulay2/packages/MinimalPrimes/doc.m2) says the opposite: *"`minprimes` and `decompose` are synonyms for `minimalPrimes`."* They have not been synonyms since 2008.

So a reader who follows `decompose` to the core documentation is told it is a general
verb, and one who follows it to `MinimalPrimes` is told it is a synonym. Reconciling
those two sentences, and stating `intersect decompose I == radical I` alongside a pointer
to `primaryDecomposition`, would settle what this issue is actually about.
