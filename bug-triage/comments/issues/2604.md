Still broken with a newer compiler, and this time with a same-tree control.

The thread only ever tested GCC 12 — 12.0.1 and 12.2.0 here, 12.2.1 for @jkyang92 — so Dan's
question about comparing versions to see whether the LTO bug had been fixed was never answered.
It has not been. On GCC 13.3.0 / Ubuntu 24.04, building today's development tree twice from the
same source with `--with-system-libs` and identical `dpkg-buildflags`, differing only in whether
`-flto=auto -ffat-lto-objects` was stripped:

```
LTO:      -- topBuilddir     = .../lto-build/
          -- SIGSEGV
          make: *** [.../Core/tvalues.m2] Error 1

control:  -- topBuilddir     = .../nolto-build/
          -- topSrcdir       = .../M2/M2/
          -- coredir         = .../share/Macaulay2/Core/
          Macaulay2, version 1.26.06
          -- phase 2 / 3 / 4        exit 0
```

It dies exactly where you pinned it in 2022, at the `get(topBuilddir|"srcdir")` call — now
`startup.m2.in:347-348`. The stack trace matches the original frame for frame:
`evaluate_evalraw` / `applyFCC` / `evalraw` / `applyFCC` / `evalraw` … `applyFCCS` / `evalexcept` /
`readeval3` / `readeval`, with `readeval` still carrying the `[clone .lto_priv.0]` marker. Only the
line numbers moved with the source. Nothing has changed on either side of the interaction: `getfun`
is still `actors4.d:728`, the `get` call is still where it was, and there is no LTO handling anywhere
in `configure.ac` or the cmake files.

It has also recurred independently. #3765 (Arch, May 2025) is the same crash at the same
`tvalues.m2` step with the same `.lto_priv.0` marker, and was resolved the same way — by turning LTO
off in the PKGBUILD, not by fixing anything.

What this does not explain is why @mahrud's Fedora builds were fine with GCC 12 and LTO on; that
question is still open, and the answer probably matters for narrowing this down to something
reportable upstream.

Worth noting that the workaround is load-bearing rather than historical: `dpkg-buildflags` still
emits `-flto=auto -ffat-lto-objects` by default here, so anything that builds M2 with distribution
defaults and does not override them gets the segfault.
