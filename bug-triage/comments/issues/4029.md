Closing this as expected behaviour, with the explanation you asked for. Taking your questions in
order: it is not a bug in `sub`, your `ambient` workaround is the right answer and there is a
reason it works — and your example turns up a genuine bug somewhere else, which is tracked
separately.

### Why `t^7`

In `GF 9`, `a-1` and `a^7` are not two spellings of one element. They are the same object:

```m2
i1 : k = GF 9; a = k_0;

i3 : a-1 == a^7
o3 = true
```

A `GaloisField` stores its elements as powers of the primitive element, so there is no polynomial
representative for `sub` to act on — it substitutes into the exponent form the element actually
has, and `a^7` goes to `t^7`. Nothing is lost or mangled on the way.

`ambient GF 9` is `(ZZ/3)[a]/(a^2-a-1)`, an honest quotient of a polynomial ring, whose elements
*do* carry polynomial representatives. That is why the same substitution there gives `t-1`. So the
answer to your closing question — how to replace `a` by `t` in a representative of `a-1` — is
exactly the thing you had already found, and it works because `ambient` is where representatives
live.

### Why it is not a bug

`map(T, T, {t, t})` is not a ring homomorphism at all. `a` is algebraic over `ZZ/3`, satisfying
`a^2 = a+1`; `t` is transcendental. There is no homomorphism sending `a` to `t`, so there is no
correct answer for `sub` to give, only a choice of which representation to push forward. M2 does
not enforce well-definedness of ring maps — that non-enforcement is the subject of #1011, where
@DanGrayson asks for it to be documented, noting that ill-defined maps do not behave as expected
and that even composition can disagree with successive application.

### The part that *is* a bug

You wrote that you think this is really an issue with ill-defined ring maps. It is, and more
sharply than you put it — M2's own detector does not flag this map:

```m2
i1 : T = GF 9[t];

i2 : isWellDefined map(T, T, {t, t})
o2 = true

i3 : U = (ambient GF 9)[t];

i4 : isWellDefined map(U, U, {t, t})
o4 = false
```

`true` is wrong. That is #3961: `isWellDefined RingMap` checks only that the relations of the
source die under the map. Once `GF 9` is a *coefficient* ring rather than the ring itself, there
are no relations left to check:

```m2
i5 : ideal first flattenRing(GF 9[t], Result => 3)
o5 = ideal ()

i6 : ideal first flattenRing((ambient GF 9)[t], Result => 3)
o6 = ideal(a^2-a-1)
```

The test is vacuous in the first case, so the coefficient ring is never examined — which is the
same reason `isWellDefined map(ZZ[x], (ZZ/5)[x])` wrongly returns `true` on #3961.

So the guard you would reasonably reach for to detect the situation is the one that fails on it,
and that is worth knowing before relying on it.

So of the two things this issue raises, neither needs to stay open here: the `sub` behaviour is
working as designed, and the ill-defined-ring-map half you point at is covered by #1011 (that the
documentation should say M2 does not enforce well-definedness) and #3961 (that `isWellDefined`
gets these maps wrong). Please reopen if you think the reasoning above is off.
