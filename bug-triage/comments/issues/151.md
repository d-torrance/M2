Closing as not reproducible, from a sweep of the open issues — but the mechanism behind it
is still tracked, at #175, so please read on before treating this as "went away".

### It does not reproduce

57 runs of `check "NumericalAlgebraicGeometry"` on 1.26.06-40, looking for the signatures
in this report — `SIGSEGV`, libgc's `Duplicate large block deallocation`, and any stack
trace:

```
57 runs, 0 with a crash signature
```

The original rate was about one in twenty, so seeing none in 57 runs has a probability of
roughly 5% if the fault were still present at that rate. The one failure that does occur is
deterministic and unrelated — `check(41, ...)` fails with
`no method found for applying bertiniRefineSols`, because Bertini is not installed on this
machine.

### The suspected trigger is gone

Dan pinned it on the mpfr version and rolled it back to 3.0.1 as a workaround. That version
question no longer exists: M2 here links `libmpfr.so.6`, which is mpfr 4.x. Nothing in the
tracker reports a comparable SIGSEGV in this package since 2014.

### What is *not* gone, and where it lives now

The cause was never actually found here — the thread ends with four commits handed over to
make the behaviour more deterministic for debugging, and nothing after that. But it did get
written down. Two months later Dan opened **#175**, describing what is recognisably this
defect in general terms:

> Some of our code and many of our third party libraries are not thread safe, and some of
> those that are, such as mpfr, achieve thread safety in a way that makes our use of libgc
> break, by storing libgc pointers in thread local variables in locations unknown to the
> libgc garbage collector.

That is the same collision — mpfr, libgc, and pointers the collector cannot see — stated as
the general problem rather than as one package's crash. #175 is open, and carries a
checklist from @mahrud dated 2025-07-05 for the interpreter side of it.

So this issue is being closed as the stale instance, not as a solved problem. The umbrella
is #175. Related, and also open: #143, where memory-allocating tasks still get 1.78x of a
possible 4.0x speedup while non-allocating tasks get a perfect 4.0x — the same GC
serialisation seen from the performance side rather than the crash side.

**If anyone sees a SIGSEGV or a `Duplicate large block deallocation` in this package again,
please reopen** — 57 clean runs is good evidence and it is not proof, and a nondeterministic
memory fault is exactly the kind that hides.
