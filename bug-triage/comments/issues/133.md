@fragandi — some context on your question, from a sweep of the open issues, since it has
been sitting unanswered.

**The message you are looking at changed by accident, not because anyone acted on this
issue.** The wording came from
[`0819a1403c`](https://github.com/Macaulay2/M2/commit/0819a1403c) (2022-08-28,
"turned kernel RingMap into hooks"): the old string was replaced in the course of
converting `kernel RingMap` to the hooks mechanism, and the error is now raised at
[`m2/ringmap.m2:236`](https://github.com/Macaulay2/M2/blob/development/M2/Macaulay2/m2/ringmap.m2#L236)
as the fallback when no hook claims the map. So the improvement was real but incidental,
and nobody has weighed in on whether it says enough — which is what you are asking.

Current state on 1.26.06-40:

```
i1 : R = ZZ[x]

o1 = R

o1 : PolynomialRing

i2 : f = map(R,R)

o2 = map (R, R, {x})

o2 : RingMap R <-- R

i3 : ker f
stdio:3:3:(3):[1]: error: kernel: no method implemented for this type of ring map
```

Two things worth knowing before picking wording.

**The cause is narrower than "not over a field" may suggest.** The message is now the
no-hook fallback, so it fires for any ring map no installed hook handles. Wording that
names the coefficient ring specifically — your option 2, "ONLY for maps of rings over
fields" — would be a claim about the whole method table rather than about this call, and
would go stale the first time somebody adds a hook for another class of map. Something
closer to your option 1, which describes what is missing rather than what is required,
survives that.

**There is a live proposal to remove the error entirely.** #1518 reports this same
reproducer — `R = ZZ[x]`, a ring map, `ker` — and asks for the operation to be implemented
rather than for the message to be improved, recording that Mike said at an M2 internals
meeting that it can in principle be turned on. If that happens, the `ZZ` case stops
erroring at all and any wording chosen now describes a case that no longer arises. The two
issues are not duplicates — this one is about the message, #1518 is about the
functionality — but they share a reproducer, and it is worth knowing which one you would
rather spend the effort on.

Neither of those is a reason not to improve the message; both are things to know first.
