### Why it says `false`

`isSupportedInZeroLocus(Ideal, Module)` has two routes. The one that runs in your example builds
a fresh ring and works there
([`Saturation.m2:636-646`](https://github.com/Macaulay2/M2/blob/development/M2/Macaulay2/packages/Saturation.m2#L636-L646)):

```m2
R := (coefficientRing S)[(S_*)_perm,
    MonomialSize  => 16,
    MonomialOrder => {Position => Up, n - #supp, #supp}];
G := groebnerBasis(sub(presentation M, R), Strategy => "F4");
```

For `S = QQ[x,y]/(x^2+y^2)`, `coefficientRing S` is `QQ` and `S_*` is `{x,y}` — so `R` is the
**polynomial ring** `QQ[x,y]` and the relation `x^2+y^2` is dropped. The question actually
answered is about `coker(x)` over `QQ[x,y]`, which has dimension 1, rather than about `M3` over
`R2`, which has dimension 0:

```m2
dim coker sub(presentation M3, QQ[x,y])   -->  1
dim M3                                    -->  0
```

So your diagnosis is right that the relation is being ignored, but not in the way you expected:
the annihilator is computed correctly and *does* already contain `y^2`, since `y^2 = -x^2` in
`R2` —

```m2
annihilator M3                 -->  ideal x
y^2 % (annihilator M3) == 0    -->  true
isSubset(m^2, annihilator M3)  -->  true
radical(annihilator M3) == m   -->  true
```

— all of which say the answer should be `true`. And "translate the problem to work over the
polynomial ring", which you propose at the end, is exactly the step that loses the relation.

### The other route is correct, and is usually skipped

The first branch returns `saturate(annihilator M, B) == ideal 1`, and here that is `true`. But it
returns only when the saturation is *already computed*; otherwise the branch falls through to the
one above. That is why running `annihilator M3` first did not help you — the annihilator gets
cached, the saturation does not. Running both does:

```
fresh                                     -->  false
after  annihilator M3                     -->  false
after  annihilator M3 and saturate(N, m)  -->  true
```

Each in a separate session, since the next point makes in-session testing unreliable.

### It rebinds your ring variables

Building `R` from `(coefficientRing S)[(S_*)_perm, ...]` binds the symbols `x` and `y` to the new
ring's generators, so a call to `isSupportedInZeroLocus` silently moves the caller's variables out
from under them:

```m2
i5 : ring x === R2

o5 = true

i6 : isSupportedInZeroLocus(m, M3);

i7 : ring x === R2

o7 = false

i8 : ring x

o8 = QQ[x..y]

o8 : PolynomialRing
```

After the call, `x` lives in that `MonomialSize => 16` product-order ring, and the next expression
using `x` fails with `expected matrices for compatible rings`. This is independent of the wrong
answer and would still be worth fixing even if the answer were right.
