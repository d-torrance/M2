Half of what this issue asked for was done, and the thread never says so — so here is where it
stands, and what the remaining half now involves.

### The archive proposal was carried out in 2020

@DanGrayson's *"Let's move all of those into a subdirectory called `archive` except for
NCAlgebra"* happened in `fecbbf8aef` (2020-07-08), under the name
`packages/undistributed-packages/`. Of the 27 distinct packages in the list above:

| | |
| --- | --- |
| moved to `packages/undistributed-packages/` | 23 |
| kept in `packages/` and distributed | `NCAlgebra`, as asked |
| became distributed packages instead | `Python`, `SubalgebraBases` |
| deleted outright | `Flint`, in `60177fb76a` (2020-04-12) |

That closed the practical hole for all of them, and for a reason worth stating: a package under
`undistributed-packages/` is not on the load path either, so a distributed package that depends
on one now fails **in the source tree, during our own tests** — which is exactly the failure
mode the issue opens by saying we would never catch.

Today `NCAlgebraV2.m2` is the only file in `packages/` that is not on `=distributed-packages`.
Nothing distributed depends on it: `AssociativeAlgebras`, `PathSignatures` and `gfanInterface`
all reference `NCAlgebra`, which *is* distributed. So the structure that permits the bug is
intact, but it currently has no instance.

### The remaining half, and what makes it harder than deleting a file

The other proposal — *"remove the list `=distributed-packages` and distribute all packages found
in the directory `packages`"* — is untouched. The list is not only a set of names; the hope is
that its **order** is a topological sort of the dependency graph, so a serial build installs
each package after the ones it needs.

It is not one any more. Reading all 299 headers with `readPackage` and comparing each
`PackageImports` / `PackageExports` entry against its position in the file gives **110 edges
pointing the wrong way**, involving 36 distinct packages that would have to be installed before
something listed above them. Two that can be checked by eye:

- `Benchmark` is line 7, with `PackageImports => {"Complexes", "XML"}`. `XML` is line 56 and
  `Complexes` is line 172.
- `Saturation` is line 11, with `PackageExports => {HomologicalAlgebraPackage, "Elimination"}`.
  That symbol resolves to `Complexes` (line 172), and `Elimination` is line 20.

`Complexes` accounts for 47 of the 110 — `Benchmark`'s edge arrived in `bcf0c24698` this
January, with the `OldChainComplexes` → `Complexes` migration, which added a batch of upward
edges that nothing flagged. But the drift is not only that migration's doing: **63 of the
violations do not involve `Complexes` at all**, the next worst being `Isomorphism` (6),
`Elimination` (5) and `MinimalPrimes` (5).

Nothing has broken, because nothing actually depends on the order. Both build systems declare
only the three global prerequisites — every package depends on `Style`, `FirstPackage` and
`Macaulay2Doc` (`packages/Makefile.in:112-114`, `Macaulay2/packages/CMakeLists.txt:153`) and on
nothing else. So the file's order takes effect only as serial `make`'s left-to-right
prerequisite order, and `make -j` ignores it entirely. Even a *correct* topological sort would
buy nothing in a parallel build, which is the build everyone actually runs.

### So the replacement should be computed, not listed

Which makes @mahrud's 2020 suggestion above the right shape for this: use `readPackage` to
derive the dependencies and turn them into real prerequisites between the install targets, then
the order of any list stops mattering and parallel builds get correct ordering for the first
time. `readPackage` exists now — #1085, which asked for it, is closed — and reading all 299
headers takes one pass; that is where the numbers above came from.

`M2/Macaulay2/CMakeLists.txt:16` already carries a bare `# TODO: discontinue using this list`.
The point of this comment is that discontinuing it is not a loss of ordering information,
because the ordering information in the file has already decayed to the point where it is not
worth preserving — it is worth recomputing.
