Closing this, because `./configure` already does what is being asked — and the one part it
deliberately does not do is the part @DanGrayson objected to above.

**Version checks are there, and some predate this issue.** `M2/configure.ac` carries minimum-version
tests for flint (`>= 2.6.3`), mpfr (`>= 4`, needed for `mpfr_nrandom`), tbb (`>= 2020`), boost
(`>= 1.65`), readline (`>= 6`), gmp (`>= 6.2.1`) and factory. The factory one is spelled with exactly
the `MINVERSION` variable proposed here:

```sh
FACTORY_MINVERSION=4.2.0
if $PKG_CONFIG --exists "factory >= $FACTORY_MINVERSION"
```

That line was added in `8b2e430b46`, in 2015 — four years before this issue. Feature tests are used
too where they are sharper, which is @DanGrayson's stated preference:
`AC_CHECK_HEADERS([flint/nmod.h])`, commented *"only present in flint >= 2.9.0"*.

**What is deliberately not done is matching `M2/libraries/*/Makefile.in`.** The two serve different
purposes: `configure` tests a *system* library to decide whether it will work with M2, while
`M2/libraries` builds a library for us when the system's will not do. So the numbers are meant to
differ, and they do:

| | `configure` accepts | `M2/libraries` builds |
| --- | --- | --- |
| flint | `>= 2.6.3` | 3.6.0 |
| factory | `>= 4.2.0` | 4.4.1 |
| mpfr | `>= 4` | 4.2.2 |

That gap is the point. `M2/libraries` tracks the newest release; `configure` accepts anything known
to work, which is what lets M2 build against libraries already present on older systems. Tightening
the first to match the second would remove that, which is what @DanGrayson meant by *"there is no
reason to try to match the version numbers in our library makefiles."*

@mahrud — to answer your 2020 question directly: closing, rather than keeping it open for an
autotools equivalent of `cmake/check-libraries.cmake`. Autotools has its own checks; they are just
not written as a version table.
