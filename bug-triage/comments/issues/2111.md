Closing as a duplicate of #1984, which is two months older, is the same `superRing` call in the same
package, and carries a diagnosis that accounts for both crash signatures.

That diagnosis is that nested `superRing` builds a ring whose joined `MonomialOrder` repeats the
coefficient ring's blocks, and that `ALLOCATE_EXPONENTS` uses `alloca` without zeroing — so stack
garbage gets read as exponents. Which symptom you get depends on where the garbage lands: a
`monomial exponent overflow` when it falls in a GRevLex slot, a segfault when it falls in a length or
a size. That covers the `getSequenceOfSmallIntegers` trace here and the `getmem_atomic` one in the
2024 comment.

Two caveats, since this is being closed on circumstantial grounds rather than a demonstration. The
identity is inferred from the shared call and the shared intermittency, not from tracing one garbage
read to the other. And the three lines above build cleanly on 1.26.06 here, three runs in a row —
which is not evidence of a fix, because #1984 was still terminating a macOS CI job on 2026-08-04.

One thing this pairing does settle: the fix attempted in #4361, wrapping `RingElement`'s arithmetic
in `try`/`catch`, cannot be the whole answer if these share a cause. A segfault in `getmem_atomic` is
not a C++ exception and no `catch` will see it. The garbage has to be stopped at the source rather
than trapped downstream.
