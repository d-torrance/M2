Still happens on 1.26.06, and one detail in the report is the wrong way round: `degreeLength SM` is
3, so `{1}` is the malformed argument and `{1,0,0}` is the well-formed one. Calls with both
arguments of length 3, or both empty, are deterministic and correct; only the short ones vary from
run to run.

The reason they vary is that `degree_in_box` (`M2/Macaulay2/e/free-modules/freemod.cpp:391`) loops
`i` up to the ring's degree rank while indexing `lo->array[i]` and `hi->array[i]`, whose only length
check is `!= 0` — so a short vector reads past the end of the array. Nothing below the M2 level
catches it: `d/interface.dd:1877` checks only that the arguments are sequences of small integers.
It does need `debug Core` to reach, though, because the one caller in Core, `submatrixByDegrees`
(`m2/matrix.m2:499`), validates the lengths itself and errors with "expected degree vector of
length 3".

Which makes the second comment here the interesting one: partial degrees are exactly the input that
currently reads garbage, so giving them a meaning would settle both halves of this issue at once.

Not the same as #3578, incidentally — that one passes correct-length degrees and goes wrong on
torsion in the degree group, so neither closes into the other.
