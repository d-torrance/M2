Not intended behaviour, and it is worth saying where it actually lives: `fan` is not doing anything
wrong — **`linealitySpace` of a cone is not a function of the cone.** It depends on whether `rays`
has been computed first.

Two cones built from identical H-data, differing only in that the second has had `rays` asked of it:

```m2
i4 : A = coneFromHData(v1, v2);

i5 : LA = image linealitySpace A;

i6 : B = coneFromHData(v1, v2);

i7 : rays B;

i8 : LB = image linealitySpace B;

i9 : LA == LB

o9 = false

i10 : (rank LA, rank LB)

o10 = (8, 8)
```

Both are rank 8, so neither is degenerate — they are two different 8-dimensional subspaces of
`ZZ^10`, and one of them is simply wrong.

That accounts for your example exactly. `fan Cone`
(`Polyhedra/core/fan/constructors.m2:119-123`) computes the rays before the lineality space:

```m2
fan Cone := C -> (
   raysC := rays C;
   linealityC := linealitySpace C;
```

so a fan always carries the rays-first answer, while a cone you have only just constructed gives the
other one. Comparing the two is comparing the two branches.

It also explains why this looked like *"some rare instances"*. It is not the input that is rare — it
is whatever you happened to evaluate earlier in the session. Anything that forces `rays` on the cone
first, including comparing two cones with `==`, makes the disagreement vanish:

| | |
| --- | --- |
| `image linealitySpace(fan C1) == image linealitySpace C2` | `false` |
| the same, with `C1 == C2` evaluated first | `true` |

So the thing to fix is upstream of fans: `compute#Cone#computedLinealityBasis`
(`core/cone/properties.m2:186`) chooses between three different computations depending on which
properties the cone happens to have cached when it is first called, and those do not all agree.
