Retested on both platforms in August 2026. The diagnosis in this thread still holds on
macOS, no longer holds on Linux, the macOS failure is worse than recorded here — and there
is a workaround that works on both today. Options for a real fix at the end.

### The platform split

`M2` is still a `/bin/sh` wrapper on both platforms — `/usr/bin/M2` on Debian,
`/opt/homebrew/bin/M2` on macOS — so everything turns on whether the kernel will resolve an
interpreter that is itself a script.

**macOS 26 (Tahoe), Apple M5 Pro, Homebrew.** It will not:

```
$ python3 -c 'import os,sys; os.execv(sys.argv[1],[sys.argv[1]])' hello.m2
OSError: [Errno 8] Exec format error
```

**Linux 6.8.** It will, and it is the kernel rather than a shell fallback — verified through
`os.execv` with no shell in the picture:

```
$ python3 -c 'import os,sys; os.execv(sys.argv[1],[sys.argv[1]])' hello.m2
OK -- shebang ran
```

Linux permits a bounded chain of script interpreters; macOS returns `ENOEXEC` and stops.
Neither is wrong — POSIX does not require the recursion, so Linux's behaviour is the
extension.

### The part not recorded here: on macOS it does not fail cleanly

Run from a shell rather than through `execve`, the shell catches the `ENOEXEC` and falls
back to interpreting the file **as a shell script**:

```
hello.m2: line 2: stderr: command not found
exit status: 127
```

The lines of the `.m2` file are being *executed by `/bin/sh`*, not rejected. Almost every
line of M2 source is "command not found", which is how this presents, but any line whose
first word happens to name a shell command will do whatever that command does. So the
failure mode differs by invocation path: a clean `ENOEXEC` through `execve`, a silent
misinterpretation through a shell.

### Workaround that works today, on both

Point the shebang at the binary instead of the wrapper:

```m2
#!/opt/homebrew/bin/M2-binary --script
```

`M2-binary` is a real executable, so there is no nesting to resolve. Confirmed working on
macOS (shell, exit 0) and on Linux (shell and `execve`, exit 0). It works because the
wrapper turns out to be redundant on both of these installs — `env -u LD_LIBRARY_PATH
M2-binary --version` succeeds on Debian, and the Homebrew build likewise, since both already
carry a usable rpath.

Also worth knowing for any of the options below: **M2 ignores the shebang line itself.**
Feeding it a file starting `#!/nonexistent --script` runs the rest without complaint, so
none of this needs parser work.

### Three ways to fix it properly, with the trade-offs

**1. Documentation only** — publish `#!<prefix>/bin/M2-binary --script` as the supported
form and correct the `changes, 1.0 and 1.1` text.
*For:* no code, no build changes, no packaging risk, works on both platforms now.
*Against:* it promotes `M2-binary`, an implementation detail, to public API, and commits to
keeping that name. The path differs per install and cannot be found through `env`. And it is
only sound while the wrapper stays redundant — a from-source build into an unusual prefix is
exactly the case where `LD_LIBRARY_PATH` matters, and such a script would silently lose it.

**2. Ship `M2` as a compiled shim** — a small executable that sets the environment and
`execv`s `M2-binary`, replacing the shell script.
*For:* the idiom this project already documented starts working everywhere, unchanged, and
every existing script keeps working. Keeps whatever environment setup the wrapper does, so
no assumption that rpath is sufficient. No rpath surgery at install time.
*Against:* a new C file and build rule. The one piece of real work is that the shim must
locate `M2-binary` relative to itself — the script uses `dirname "$0"`, and the portable
equivalent is `/proc/self/exe` on Linux and `_NSGetExecutablePath` on macOS. Slightly less
transparent than a shell script somebody can read.

**3. Drop the wrapper — bake the rpath in at install time**, the fix proposed in this thread
in 2015: `install_name_tool` on macOS, `patchelf` or `chrpath` on Linux.
*For:* the simplest end state. One executable called `M2`, no indirection, shebang works,
nothing extra to maintain. The evidence it is achievable is above — `M2-binary` already runs
standalone on both installs tested.
*Against:* relocatable rpath is fiddly (`$ORIGIN` on Linux, `@executable_path` on macOS),
and the failure mode is a binary that will not start rather than one that starts slowly. The
wrapper currently branches three ways — cygwin sets `PATH`, darwin `DYLD_LIBRARY_PATH`,
everything else `LD_LIBRARY_PATH` — so each needs its own answer. Distributions already
override this and would be unaffected either way; the people affected are those building
from source, who are also the ones most likely to use an unusual prefix.

2 and 3 are not exclusive: a shim now is reversible, and rpath work later would let the shim
be deleted rather than rewritten. 1 is worth doing regardless of which is chosen, since the
documented idiom is currently wrong on macOS whatever else happens.
