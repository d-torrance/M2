Closing this. The cap was never added — `installPackage` still runs every example and only raises
at the end — but the reason given for wanting one is already adjustable, and it is adjustable
because M2 is what switches core dumps on in the first place.

### M2 raises the core limit itself

`m2/run.m2:13` builds the prefix for every example subprocess as

```m2
ulimit := utest "-c unlimited" | utest "-t 700" | utest "-m 850000" | utest "-s 8192" | utest "-n 512"
```

and `SetUlimit` is part of `defaultMode` (`m2/run.m2:85`), so any example that falls through to the
external path (`m2/examples.m2:259`) runs under `ulimit -c unlimited`. On a typical Linux shell the
soft limit is `0` and the hard limit is `unlimited`, so that line is precisely what turns the large
files into a possibility.

### Which means it can be turned off without changing `installPackage`

```m2
i1 : debug Core

i2 : runString(///run "ulimit -c"///, Core, false)          -- default
unlimited

i3 : argumentMode = defaultMode - SetUlimit;

i4 : runString(///run "ulimit -c"///, Core, false)          -- same call, no ulimits
0
```

Two things worth knowing before reaching for it:

- `argumentMode` and `SetUlimit` live in Core's private dictionary, so `debug Core` is needed —
  without it `argumentMode` is just an undefined symbol and the assignment quietly does nothing to
  the subprocess.
- `SetUlimit` is all or nothing. Dropping it also drops `-t 700`, `-m 850000`, `-s 8192` and
  `-n 512`, so a runaway example loses its 700-second CPU cap along with its core limit.

`m2/testing.m2:138` and `m2/startup.m2.in:522` both already do exactly this, which is the pattern
to copy.

If it turns out that what is really wanted is a cap on failures for its own sake — the wall-clock
cost of running hundreds of failing examples rather than the disk cost of their core files — that
is worth a fresh issue stating it that way.
