Closing this as `wontfix`. It came out of the `bugs/` sweep on the strength of Dan's one-line note,
and looking at it properly the objection doesn't survive.

**M2 already uses this extension by hand, outside the code generator.** `Macaulay2/d/xml-c.c:19` is

```c
static void initxml() __attribute__ ((constructor));
```

built whenever `WITH_XML`. So removing the attribute from `scc`'s output would not leave M2's C
standard-conforming — it would leave one hand-written use behind.

**It is also the only GNU C extension in play.** Across the hand-written C in `Macaulay2/c` and
`Macaulay2/d` there are no uses of `typeof`, `__builtin_*`, `asm`, statement expressions,
`__extension__`, or computed goto; the only other `__attribute__` is in the vendored
`pythoncapi_compat.h`. And it isn't diagnosable as a conformance problem anyway —
`gcc -std=c11 -pedantic-errors` compiles the declaration above without a word, because
`__attribute__` lives in the double-underscore namespace the standard reserves for implementations.
Only the semantics, running code before `main`, are outside the standard.

### What dropping it would actually involve, for the record

The attribute is load-bearing rather than decorative. `c/chk.c:1203-1221` generates each
`<pkg>_prepare` so that it runs the file's own initialisation and then **self-registers** two hooks:
`this_thread_prepare` onto `thread_prepare_list` and `this_final` onto `final_list`. So the explicit
lists M2 already has are *populated by* the constructors and can't replace them —
`bin/main.cpp:186-190` says as much in a comment, and `reverse_run(thread_prepare_list)` at
`main.cpp:169` only works because the constructors have already run.

A replacement is feasible: `_prepare` is generated with `export_F`, so it is externally visible, and
its name is deterministic, so a generated master initialiser called first from `main` would do the
job — the existing `called_yet` guard even makes double-calling harmless. The cost is ownership of
the cross-file ordering, which the loader currently chooses and nobody has had to specify.

That refactor might be worth doing on its own merits, since unspecified constructor order is a
footgun and is presumably why `_thread_prepare` got an explicit list in the first place. But it is a
different proposition from ANSI conformance, and worth its own issue with its own motivation if the
ordering ever causes a real problem.
