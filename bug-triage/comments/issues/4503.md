Closing this: the two results are not inconsistent, and `1p10` has nothing to do with them. This
issue came out of the `bugs/` sweep on the strength of Dan's *"This looks like a bug!"*, and the
answer is that the two literals are different numbers.

```m2
i1 : toExternalString 1.0000000000000001

o1 = .1p53e1

i2 : toExternalString 1.000000000000001

o2 = .10000000000000011p53e1
```

The first rounds to **exactly 1** at 53 bits; the second does not. So the same pair of answers
appears with no low-precision number involved at all:

```m2
i3 : 1.0000000000000001 == 1

o3 = true

i4 : 1.000000000000001 == 1

o4 = false
```

`1p10 == 1.0000000000000001` is therefore `1 == 1`, and `1p10 == 1.000000000000001` compares 1
against something that genuinely differs from it. Both are right.

### The question that does survive, for anyone who wants it

`==` compares exact values rather than at the lower of the two precisions:

```m2
i5 : 1p10 == 1.0000001

o5 = false
```

Those two agree to 10 bits, and `1p10` carries only 10 bits, so an argument could be made that this
should be `true`. That is a proposal about mixed-precision comparison, though, not the inconsistency
this issue reports — and it deserves its own issue with that example if anyone wants to pursue it.

### The same surprise, from the other direction, is #708

Worth pointing at [#708](https://github.com/Macaulay2/M2/issues/708), still open, because it holds
the mirror image of what happened here. There, in @d-torrance's comment of 2025-01-19:

```m2
i1 : 1.0 + 2^(-52)

o1 = 1

o2 = false        -- oo == 1
```

A value that *prints* as `1` and is *not* equal to `1`. Here it was the reverse: a literal that
prints as `1` and **is** `1`. Both come from the same place — the digits M2 chooses when turning a
binary float back into decimal do not distinguish values that `==` distinguishes, in either
direction.

That is what #708 is really about by now, and the fix it wants is a shortest-round-trip conversion
(Dragon4, Grisu3, Ryū) rather than `mpfr_get_str`'s closest-representation. So anyone whose interest
in this issue was "M2's decimal output is misleading" should read #708 rather than reopen this one.
