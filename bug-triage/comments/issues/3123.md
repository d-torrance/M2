Still wrong on 1.26.06, and the cause is visible one level down: the flattened ring marks **every**
variable skew.

```m2
i3 : x_1*y_2

o3 = -x y
       1 2

i4 : y_2*x_1

o4 = x y
      1 2

i5 : (options S).SkewCommutative

o5 = {0, 1, 2, 3}

i6 : (options first flattenRing S).SkewCommutative

o6 = {0, 1, 2, 3, 4, 5, 6}
```

`S` itself is right — its four `y`'s are the skew ones. But `SkewCommutative` is a flat list of
variable indices, so flattening a tower of two skew rings unions the two blocks into `{0..6}`, and
there is then no way left to record that the `x`'s and `y`'s should skew-commute *within* each block
while commuting *across* them. All seven anticommute, which is the reported `-x_1*y_2`.

The controls put the fault exactly there — it is the both-skew case and nothing else:

| coefficient ring | top ring | `base * top == top * base` |
| --- | --- | --- |
| `QQ[x_1..x_3, SkewCommutative => true]` | skew | **false** |
| `QQ[a_1..a_3]` (commutative) | skew | true |
| `QQ[c_1..c_3, SkewCommutative => true]` | commutative | true |

So this does not look like a sign error to hunt down in the multiplication code — it is a
representational gap. Any fix has to give `SkewCommutative` a way to express block structure across
a tower, or else stop flattening these towers into a single skew ring.
