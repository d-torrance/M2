The second of the two options offered here exists now, and @mahrud added it himself:
`59ea23120c` introduced the `breakpoint` keyword, which shipped in #3431 and first appeared in
1.25.05. That was a pull request about top-level profiling, which is why nothing ever linked it
back to this issue. `interp.dd` handles the `continue` command from a breakpoint by evaluating
the code rather than re-entering the debugger, so on 1.26.06:

```m2
i2 : f 12
12
bp.m2:3:20:(3): entering debugger (enter 'help' to see commands)
bp.m2:3:15-3:36: --source code:
    breakpoint print "at breakpoint";

ii3 : continue
bp.m2:3:20:(3):[2]: unhandled continue command
at breakpoint
12

o3 = 12
```

That `12` is the output this issue said it should have got.

Leaving the issue open for three loose ends, all of them in the part of the report that asked
for the behaviour to be clarified rather than changed:

- `error 0` as a breakpoint is unchanged: `continue` still re-runs it and loops.
- The debugger help still reads `continue -- leave the debugger, continuing execution with
  current expression` (`m2/code.m2:261`), which is the wording called out above as not matching
  what happens.
- `continue` at a real breakpoint prints `unhandled continue command` before doing the right
  thing.
