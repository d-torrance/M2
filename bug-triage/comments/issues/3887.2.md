**Correction to my comment above.** I wrote that "what distinguishes the two rings is the
**degree rank**, not the monomial order", and that the degree rank was "sufficient on its own".
That is true of one of the two failures in this issue and false of the other — and it is false
of the one @kschwede opened with, the push forward coming back at rank 2 instead of 6.

The `newRing(S2, MonomialOrder => GRevLex, Degrees => {1,1})` workaround changes **two** things
about `S2`, and my transcript only ever exercised `myFun`. Changing them one at a time:

| ring | degree rank | monomial order | `prune` of the pushFwd module | `myFun(x)` |
| --- | --- | --- | --- | --- |
| `S2`, as `flattenRing` returns it | 2 | product | **`QQ^2` — wrong** | **error** |
| `newRing(S2, Degrees => {1,1})` | 1 | product | **`QQ^2` — wrong** | no error, but into that wrong `QQ^2` |
| `newRing(S2, MonomialOrder => GRevLex)` | 2 | one block | `QQ^6` | **error** |
| both — the workaround | 1 | one block | `QQ^6` | works |

So there are two independent faults here, and the workaround only looks like one fix because it
repairs both at once:

- the **wrong module** is controlled by the monomial order — the product order
  `{GRevLex => {1}, Position => Up, GRevLex => {1}}` that flattening assembles;
- the **`rawFreeModule: degree rank 0, but sequence of degrees given`** error is controlled by
  the degree rank, which is the part I had right.

To check it, over those four rings:

```m2
needsPackage "PushForward"
k = QQ[x]/ideal(x^3-2); L = k[y]/ideal(y^2-2); S2 = (flattenRing L)#0;
report = W -> (
    (m, g, fn) := pushFwd(map(W, coefficientRing W));
    print(degreeLength W, prune m, try toString fn(W_1) else "ERROR"));
report S2
report newRing(S2, Degrees => {1,1})
report newRing(S2, MonomialOrder => GRevLex)
report newRing(S2, MonomialOrder => GRevLex, Degrees => {1,1})
```

### Scoping that, because it does not generalise

The line above is about `S2`. **Degree rank on its own does break other cases** — including one
in #3284. On that issue's own body ring, where the degree rank is the only difference and both
rings carry a single `GRevLex` block:

```m2
R = QQ[x,y, Degrees => {{1,0},{0,1}}]/ideal(x^3-2, y^2+y+1);   -- multigraded
S = QQ[x,y]/ideal(x^3-2, y^2+y+1);                             -- singly graded

pushFwd(map(R, QQ[]))  -->  error
pushFwd(map(S, QQ[]))  -->  (QQ[])^6
```

So degree rank breaks the `QQ[]`-source case; it is the product order that costs you the rank.
(One thing there that no longer reproduces on 1.26.06: @kschwede's report that the multigraded
ring gives *a wrong answer* rather than an error when the source is `QQ` — both rings return
`QQ^6` for me.)

### What stands from the comment above

The parts that were about `flattenRing` itself all recheck: it returns degree rank 2 because it
preserves the tower's joined multidegrees; Dan's 2006 note is still an exact description of the
behaviour; `matrix2.m2:181` depends on those multidegrees to keep the flattening map
homogeneous. And the fork I named is still a real fork — it is just not the whole issue.

What the correction adds is that Dan asked about *"the degrees **and** monomial ordering"* of
`flattenRing`'s result, and both halves of that sentence turn out to have a live bug attached,
one each. My comment named the product order and then set it aside as not the active
ingredient. It is the active ingredient for the symptom in the title.
