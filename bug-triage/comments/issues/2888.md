Still fails on 1.26.06, and it turns out to be two faults stacked. Neither is about the ideal.

**Why it kills the session rather than raising an error.** The last thing printed is
`Internal error: (0,0) out of range`, from `BettiDisplay::entry` at
`e/resolution/betti.cpp:70-78`:

```cpp
int& BettiDisplay::entry(int deg, int lev)
{
  if (deg < mLoDegree or deg > mHiDegree or lev < 0 or lev > mHiLength)
    {
      std::cout << "Internal error: (" << deg << "," << lev << ") out of range" << std::endl;
      exit(1);
    }
```

`exit(1)` from library code, so there is no stack trace, nothing catchable, and any unsaved session
state is gone. That is worth fixing on its own account: it means *any* indexing slip in the
resolution code presents as an unexplained crash.

**The indexing slip.** `res2_pair` degrees are stored **relative to `lodegree`**.
`e/resolutions/res-a0.cpp:635-636` sets

```cpp
  p->degree = (short unsigned int)(generator_matrix->rows()->primary_degree(i) - lodegree);
```

and the code converts back wherever it needs an absolute degree — `lodegree + lo - 1` at `:37`,
`deg + lodegree` at `:359` and `:382`. But `betti_skeleton` (`:1817-1831`) builds an **absolute**
range and then indexes it with the relative degree:

```cpp
  int lo = lodegree;
  int hi = lo + hidegree;
  BettiDisplay B(lo, hi, len);
  ...
          int d = p->degree;
          B.entry(d, lev)++;
```

`BettiDisplay::entry` subtracts `mLoDegree` internally, so the offset is applied twice. The tell
that this is the diagnosis rather than a guess is ten lines below: `betti_remaining`,
`betti_minimal` and `betti_nmonoms` do `bettis[lev + (len + 1) * d]` on the raw array with the
same relative `d`, and they are correct — because they never moved to `BettiDisplay`.
`betti_skeleton` alone was migrated, without adjusting the convention.

So the fix looks like `B.entry(p->degree + lodegree, lev)++`. **I have not compiled or tested
that** — the diagnosis is from reading plus the measurements below, not from a patched build.

**The bug is much wider than this reproducer.** It fires whenever degree 0 falls outside the
resolution's degree range, which has nothing to do with the ring or the ideal:

| input (all with `gbTrace=3`, `Strategy => 0`) | |
| --- | --- |
| `res(coker map(S^1, S^{-1}, matrix{{a}}))` | fine |
| `res(coker map(S^{-3}, S^{-4}, matrix{{a}}))` | dies |
| `res(coker map(S^{3}, S^{2}, matrix{{a}}))` | dies |
| `res(ideal I)` | fine |
| `res(module I)` | dies |

The last pair is the reason the report reads the way it does: `comodule I` has a generator in
degree 0 and `module I` does not. Degrees 1, 2 and 3 for the generators all die equally, so it is
not about how high the degrees are — only about whether 0 is inside the range.

`gbTrace <= 2` is unaffected, and so are the default strategy and `Strategy => 1`, since only
`Strategy => 0` reaches this code.
