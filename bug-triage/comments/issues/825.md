Closing this as won't-fix, on the packaging side of the argument rather than the technical one.

The proposal here is to use libedit *"rather than building libreadline ourselves, or depending on
brew to install readline for us."* Homebrew readline is not in fact a problem in practice — it
installs, it is current, and it is what the macOS builds use — so the motivation for carrying a
second line-editing backend is thin, and a backend that has to be special-cased is not free to
keep working.

Recording where it would start, for anyone who disagrees later: `M2/configure.ac` has no
`libedit` or `editline` path at all, and the readline detection cascade ends at line 1250 with

```
AC_CHECK_DECL(rl_catch_signals,,BUILD_readline=yes, ...)
```

`rl_catch_signals` is precisely the symbol named in the report as the one libedit lacks. So
libedit is not merely unsupported — if it is what provides `readline/readline.h`, that check
fails and M2 builds its own readline anyway. Reviving this means changing that check first.

### The autocomplete remark has a better home

@mahrud's *"we should get package names to be included in autocomplete (emacs includes them, but
readline doesn't)"* is not being closed with this. It is tracked at
**[Macaulay2/M2-emacs#44](https://github.com/Macaulay2/M2-emacs/issues/44)**, which has the
actual design discussion — @DanGrayson proposing that all package symbols simply be added,
@mahrud objecting that highlighting or completing a symbol from an unloaded package would
mislead, @d-torrance proposing that `completions` from `expr.d` be exposed at top level as
`complete(String)`, and the LSP direction that came out of it. That thread is where the question
is live.

The libeditline colour patch linked above is not tracked anywhere; it would need its own issue if
anyone wants it.
