Still true for a from-source build, and there is a specific line responsible. Checked on
1.26.06-40.

### Where it goes wrong

[`M2/Macaulay2/bin/Makefile.in`](https://github.com/Macaulay2/M2/blob/development/M2/Macaulay2/bin/Makefile.in)
extracts the debug info unconditionally, then adds the debuglink only in one of two
branches:

```make
ifneq "@OBJCOPY@" "false"
	@OBJCOPY@ --only-keep-debug "$@".tmp M2.debug-info      # line 158, always
endif
ifeq "$(ENABLE_STRIP)" "yes"
ifeq (@STRIP_REMOVE_SECTION@,yes)
	@STRIP@ $(STRIP_ARGS) --remove-section=.comment --remove-section=.note "$@".tmp
else
	@STRIP@ $(STRIP_ARGS) "$@".tmp
ifneq "@OBJCOPY@" "false"
	@OBJCOPY@ --add-gnu-debuglink=M2.debug-info "$@".tmp    # line 167, else branch only
endif
endif
endif
```

`STRIP_REMOVE_SECTION` is set by `configure.ac:186-193`, which asks whether `strip --help`
mentions `remove-section`. Every GNU binutils `strip` does, so on Linux the **first** branch
is taken — the binary is stripped and `--add-gnu-debuglink` never runs. The debug info is
produced and then not connected to anything, which is the situation this issue describes.

`--add-gnu-debuglink` is itself the answer to "we have to teach gdb how to find it": it
writes the `.gnu_debuglink` section gdb looks for. It has been in the tree since
[`d6b1b11bae`](https://github.com/Macaulay2/M2/commit/d6b1b11bae) (2010), five years before
this issue, just on the branch that is not taken.

Second, and independent of the branch: `M2.debug-info` appears three times in that
Makefile — created at 158, linked at 167, removed by `clean` at 186. It is never installed.
So even with the debuglink written, there would be nothing for gdb to find after
`make install`.

### Why this is invisible on packaged builds

@mahrud's note above — that newer gdb looks in standard directories — is right, but the
mechanism is the distribution's rather than M2's. On this Ubuntu package the binary does
carry a debuglink:

```
$ readelf -S /usr/bin/M2-binary | grep debuglink
  [30] .gnu_debuglink    PROGBITS ...
$ objdump -s -j .gnu_debuglink /usr/bin/M2-binary
 0000 61393038 62306434 65646339 35393361   a908b0d4edc9593a
```

That is a build-id, not `M2.debug-info` — it is `dh_strip`'s work, with the file supplied by
the separate `macaulay2-dbgsym` package. Debian, Fedora and Homebrew all handle debug info
their own way and never reach the code above.

So the issue is live precisely for people building from source and then trying to use gdb,
which is the audience it was written for. Two small changes would settle it: move the
`--add-gnu-debuglink` call out of the `else` so it runs on both paths, and install
`M2.debug-info` somewhere gdb looks.
