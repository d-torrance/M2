Still open, and still unmeasured after seven years — so here are numbers for both halves of the
ask, and one finding that is really a warning.

Measured on x86-64 Debian, gcc 13, `include-what-you-use` 8.21, Debian's fflas-ffpack, over all 202
translation units of `e/` compiled with the flags the autotools build actually uses.

### "only include what is needed" — poor, and worst where the body says

`iwyu` over all 202 TUs:

| | |
| --- | ---: |
| unneeded includes it would remove | **397**, across 144 files |
| includes it would add | 1406, across 186 files |
| files it considers already clean | **11** of 202 |

The two worst are `basic-mutable-matrices/mat.cpp` (17 to remove, 12 to add) and
`basic-mutable-matrices/dmat.cpp` (11 to remove, 31 to add) — which are exactly the *"RingType
templates for dense and sparse matrices"* named above.

### But this cannot be done by running the tool and committing the diff

Applying `iwyu`'s 15 suggested removals to a copy of `mat.cpp` does not compile:

```
error: invalid use of incomplete type ‘class MutableMat<DMat<M2::ARingZZGMP> >’
note: declaration of ‘class MutableMat<DMat<M2::ARingZZGMP> >’
   17 | class MutableMat;
```

`iwyu` tells `mat.cpp` to drop `mutable-matrices/mutablemat.hpp`, which is where `MutableMat` is
defined and which the file's explicit template instantiations need. Applying its suggested
*additions* as well does not rescue it: one of them is `SLP/SLP-imp.hpp`, an implementation header
that does not compile standalone.

So the tool is right that the hygiene is bad and wrong about how to fix it, and it is wrong
precisely on the template-heavy files this issue is about. That is worth knowing before starting:
the passes that did run — `ddb01c6632` (headers, 2020-12-24), `0ee9bfdc0e` and `aa0b7fa644`
(`resolution/`, `schreyer-resolutions/`, 2020-12-26), `f26df24a8a` (`f4/`, 2021-01-24) and
`bf6fdbc4d2` — cover four directories and left 114 files carrying `// for ...` annotations, and
this may well be why they stopped there.

### A separate finding: one `#include` reaches a sixth of the engine

This one is about cost rather than hygiene, and the two are not the same thing.

For scale, a translation unit including `<vector>`, `<iostream>`, `<map>` and `<memory>`
preprocesses to about 58,000 lines here. **34 of the 202 TUs land between 258,000 and 347,000** —
a band only 1.34x wide from end to end, which points at one shared header rather than 34 separate
problems. All 34 reach `fflas-ffpack`; none of 25 randomly sampled lighter TUs do.

The chain, each measured on its own:

```
basic-rings/aring-glue.hpp          287,106
  basic-rings/aring-translate.hpp   272,745
    basic-rings/aring-ZZp-ffpack.hpp    258,118   <- #include <fflas-ffpack/ffpack/ffpack.h>
    basic-rings/aring-tower.hpp         258,282   <- costly only because it includes the above
```

The other fourteen `aring-*` headers that `aring-translate.hpp` pulls in are all around 80,000.

This is deliberately **not** filed as an `iwyu` problem: `ARingZZpFFPACK` exposes ffpack types in
its interface, so it may be including exactly what it needs. Reducing it would be interface work —
hiding the ffpack types behind the class boundary — not include removal, and it is a different job
from the one above.

Two caveats on all of the above: these are single-machine numbers, and preprocessed size is a proxy
for compilation cost, not a measured saving — nothing here establishes how much time any particular
fix would return.
