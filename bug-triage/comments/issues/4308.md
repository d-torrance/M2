**It isn't saturating by `(ideal vars R)` — it is returning its input.** Those two agree on the
example in the body, so here is a case that separates them: take `I = intersect(ideal(a,b), m^3)`
with `m = ideal vars S` and saturate by `J = ideal(a,b)`. Then `I:J^∞` is the unit ideal while
`I:m^∞` is `ideal(a,b)`, so the three candidate behaviours give three different answers.

```m2
i3 : I = intersect(ideal(a,b), (ideal vars S)^3);

i4 : M = S^1/I;

i5 : saturate(I, ideal(a,b))

o5 = ideal 1

o5 : Ideal of S

i6 : saturate(M, ideal(a,b)) == M

o6 = true
```

`saturate(M, J)` hands back `M` itself — `relations` are identical, not merely equal-looking. So the
ideal argument is being dropped rather than replaced by the maximal ideal.

**`topComponents` on a module does look all right, though.** On the example in the body it gives the
expected answer:

```m2
i7 : topComponents(S^1/intersect(ideal(a,b), ideal(c,d,e))) == S^1/ideal(a,b)

o7 = true
```

and on the `m^3` example above it also strips the embedded component correctly. So whatever is wrong
with `saturate(Module, Ideal)` does not seem to be reaching `topComponents(Module)`.

One pointer for whoever picks this up: it is not a missing method.
`hooks(saturate, Module, Ideal)` lists `Strategy => Decompose` and `Strategy => Iterate`, so
strategies are registered and are returning the input; the dispatch is `saturate(Module, Ideal)` in
`packages/Saturation.m2`, going through `saturateHelper`.
