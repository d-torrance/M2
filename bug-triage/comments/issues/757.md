Closing this — it no longer reproduces on 1.26.06-40-gd8e86d689d. The whole reported region is
fast, not just the boundary case:

```
minimalPrimes ideal(x^2+y^3+z^5+t*w^e)  over ZZ/7

  e =  50    0.022s     e =  80    0.019s
  e =  51    0.019s     e = 100    0.019s
  e =  60    0.133s     e = 150    0.134s
```

@kschwede's report says the exponent going *above* 50 doesn't help either, so the range matters
— a single run at 50 could pass by having landed under some new threshold, and this does not
look like a threshold effect. The `ZZ/7`, `w^50` case returns one component in 0.022s.

The controls from the report still behave as they did: `QQ`, `ZZ/5`, `ZZ/11` and `ZZ/13` are all
instant. And @DanGrayson's localization checks out as the thing that changed — `factor
(x^2+y^3+z^5+t*w^50)` over `ZZ/7`, which he noted "also takes a lot of time", now returns in
0.0005s.

### No fix is being attributed

@mahrud's 2020 stack trace puts this in `libfactory-4.1.3.so`, inside
`prodMod` / `InternalPoly::mulsame`. The build tested here links
`libsingular-factory-4.3.2`, so the change is very likely upstream in factory rather than in
Macaulay2 — M2 moved to factory 4.2.0 in `1494b858e0` and later 4.4.1 in `491b434087`, but which
upstream release actually fixed it would take going through Singular's own history, and this
issue's timeline has no cross-references to work from.

So this closes on the behaviour being gone, not on a known fix. If it comes back — particularly
on a build that bundles its own factory rather than using the distribution's — please reopen.
