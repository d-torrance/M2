Closing this, but on indirect evidence rather than on a run — so here is exactly what that
evidence is, and what it is not.

### The message is a double-free check, not memory exhaustion

`Duplicate large block deallocation` comes from `GC_freehblk` in bdwgc's `allchblk.c`:

```c
/* Check for duplicate deallocation in the easy case */
  if (HBLK_IS_FREE(hhdr)) {
    ABORT_ARG1("Duplicate large block deallocation", " of %p", (void *)hbp);
  }
```

It fires when a block being freed is already marked free. Running out of memory produces a
different message entirely — M2's `outofmem` prints `*** out of memory trying to allocate N
bytes, exiting ***`. So this report was never about the computation being too big; size only
makes it likelier that a latent double free is reached. It is also a *detector* rather than a
locator: on #35 the identical message turned out to come from an assertion failure inside mpir,
not from the subsystem it surfaced in.

### The path that could produce it from the gb engine is gone

In November 2017, when this was filed, `M2/Macaulay2/d/M2mem.c` had

```c
void freemem(void *s) {
     ...
     GC_FREE(s);
}
```

and that is what `stash::delete_elem` calls, which is what `GBRing::gbvector_remove_term` calls
for every term it removes. So the gb engine was issuing explicit frees at very high volume, and
explicit frees are what the check above catches.

@d-torrance's `1a046ba40d`, "Comment out some GC_FREE's" (2024-02-09), made `freemem` and
`freememlen` no-ops; `M2/Macaulay2/e/interface/m2-mem.cpp:99,108` now read `/* GC_FREE(s); */`,
and the one in `gbring.cpp:285` is commented out too. The engine's only remaining live explicit
free is `stash::~stash()` at `e/mem.cpp:42`.

The same pull request — **#3186, "Parallelization updates"**, merged 2024-05-05 — also carried
@DaveBarton's patch to bdwgc itself, as `89c1d5c63f`, correcting a double-counted `EXTRA_BYTES`
in `GC_generic_malloc_many`. That one is worth *excluding* rather than crediting: upstream took
the same change into bdwgc 8.2.8 (2024-09-08) and describes it as a performance fix — "poor
thread-local allocation performance because of double `EXTRA_BYTES`" — so it over-allocates
rather than corrupting anything, and it is not a candidate cause for the abort.

### What was actually tested

#2857 reports this message from `AssociativeAlgebras::oppositeRing`, is the newest of the family
(2023, so it predates the change above), and is the only one of the four with a reproducer small
enough to run. On 1.26.06-40-gd8e86d689d it completes cleanly, five runs out of five:

```m2
R = QQ[q]/ideal{q^4+q^3+q^2+q+1}
A = skewPolynomialRing(R,q,{x,y,z,w})
Aop = oppositeRing A                     -- no abort, no SIGSEGV
```

That build links the distribution's `libgc 8.2.6`, not a patched bundled copy — so those runs
are clean on an allocator that does *not* carry `89c1d5c63f`, which is the reason for setting
that patch aside above and attributing the change to the removal of the explicit frees.

#35 and #679, the other two, were both closed on the same footing.

### What was not tested, and what would reopen this

**The computation in this issue was not run.** It wants the reporter's
`GC_INITIAL_HEAP_SIZE=64G` on a 256 GB machine; under a 4 GB cap here the `gb I` completes at
2115 non-minimal elements and the `eliminate` exhausts the cap long before anything could abort.
So this closes on the class — the mechanism is no longer in the code, the underlying allocator
bug is patched, and the one member that can be checked is clean — and not on this reproducer.

@tom111, if it still aborts for you on a current build, please reopen: that would mean the
remaining explicit free in `stash::~stash()`, or something else entirely, and it would be worth
knowing.
