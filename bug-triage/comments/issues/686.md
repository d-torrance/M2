### The recomputation, and the evidence it is unnecessary

```
i1 : S = ZZ/101[s,t]; R = ZZ/101[a..d];

i2 : phi = map(S,R,{s^4, s^3*t, s*t^3, t^4});

i3 : I = ker phi;

i4 : keys I.cache
o4 = {}

i5 : gens I
o5 = | bc-ad c3-bd2 ac2-b2d b3-a2c |

i6 : gens gb I == gens I
o6 = true

i7 : keys I.cache
o7 = {module}
```

`I.cache` is empty when `ker` returns, so `gb I` starts from nothing; with `gbTrace = 3` it
registers a new computation and reports 4 gb elements, 8 spairs. But `o6` shows the answer
it arrives at is the generator matrix it was handed — the work is entirely redundant.

### Where it would go

The mechanism is as described in the report. `m2/ringmap.m2:331`:

```m2
		G := gb(graph,opts);
		ideal mapback selectInSubring(1,generators G)
```

A Gröbner basis is computed in the graph ring, the elements lying in the subring are
selected, and the result is wrapped in `ideal` — which constructs a fresh ideal carrying no
computation. There is no `forceGB` anywhere in `ringmap.m2`. The second algorithm at
`:293` has the same shape.

### Related, though not the same issue

**#996** is this problem from the other end — `ideal gens G` on a Gröbner basis you already
have also produces an ideal that must recompute. Same underlying gap (M2 discards known
Gröbner basis information at an `ideal` boundary), different entry point, so it would be
fixed in a different place; recording the link because whoever picks up one will want the
other.

**#2222** is a different request — supplying *partial* Gröbner basis information to seed a
new computation — and is not affected by this.

The body's cross-reference to #527 still holds: that issue is about `ker` passing a degree
limit through, and both are about `kernel RingMap` keeping more of what the underlying
computation knows.
