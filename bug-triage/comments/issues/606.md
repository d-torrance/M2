Closing as fixed — the stash is in the cache table now, for both chain complex types.

On 1.26.06-40, with `S = ZZ/101[a..d]`, `C = res coker vars S`, `D = C ++ C`:

| | sequence-valued keys on the object | keys in `.cache` |
| --- | --- | --- |
| `Complex` | *(none)* | `(directSum,(Complex,Complex))` |
| `ChainComplex` (via `OldChainComplexes`) | *(none)* | `(directSum,(ChainComplex,ChainComplex))` |

which is exactly what this issue asked for — *"this should be in the cache table, not in the
mutable hash table itself"* — and it holds for the legacy `ChainComplex` as well as the
`Complex` type that @mikestillman said needed it.

### The history is not monotone, which is worth recording

In May 2022 this looked settled the other way. @mikestillman asked "Is this still a problem?
I can't reproduce the error", and @DanGrayson answered:

> the value of C++C is no longer cached inside of C — not in C and not in C.cache. That
> doesn't qualify as a bug.
>
> The caching ended in version 1.17.

So as of 2022 the stash had disappeared altogether rather than moved. It is back now, and
back in the right place. Anyone reading this thread later should not take the 2022 exchange
as the final state.

I have not identified the commit that restored it, so this closes on the observed behaviour
rather than on an attribution.

### Still open from the discussion, if anyone wants it

The body proposed a specific rewrite of `directSum` in `m2/matrix.m2` and noted that
stashing does not occur for modules, "since `youngest` only applies to mutable hash tables,
and strangely doesn't apply to cache tables either". @DanGrayson explained why —

> A cache table is a special kind of mutable hash table whose hash code is 0. The age of a
> mutable hash table is defined to be its hash code — that's why `youngest` doesn't work for
> them.

— and the more ambitious suggestion in the body, making `youngest` work with cache tables so
the code can look at the youngest *cache table* of its arguments, was never taken up. That
is a separate piece of work from what this issue reports, and it is not being tracked
anywhere as far as I can see; worth its own issue if somebody wants it rather than leaving
this one open for it.
