Latest news, and it supports keeping this open for the package update rather than the version number
in the title.

The breakage reported here is gone. On 1.26.06 against normaliz 3.10.2,
`capture examples "normalToricRing(Ideal,Thing)"` completes with no error. But it was handled by a
shim rather than by an update — `Normaliz.m2:219`:

```m2
-- Until version 3.9.4, input type normal_toric_ideal was called lattice_ideal
if normalizProgram#"version" < "3.10" and nmzMode == "normal_toric_ideal" then nmzMode = "lattice_ideal";
```

and that is the pattern throughout. There are now four such version guards accumulated around an
otherwise unchanged core: this one, another for versions 3.4.0 to 3.5.1 not printing row and column
data, and two for 3.10.5 renaming `multiplicity` to `multiplicity num` and adding new keys.

Signs that the package itself has not moved:

- `Version => "2.6"`, `Date => "February 4, 2023"` — the date this issue was filed. @mahrud's
  4d76234062 that day was described as "in preparation for overhaul"; the overhaul did not follow.
- `nmzMinExecVersion` is still `"2.11"`, while normaliz is at 3.10/3.11.
- `nmzVersion` still validates against `{"norm64", "normbig", "normaliz"}` and the documentation
  still explains choosing among them and mentions using "executables of Normaliz version 2.5".
  Debian's normaliz 3.10.2 ships only `normaliz` and `normalizer`.

Work has happened since, but it is all compatibility patching: @d-torrance's edfc2e5540 (2025-06-04,
"Wrangle normaliz 3.10.5 output to match older versions") and Oliver Clarke's rational-polytope
commits of 2025-11-24.

I cannot say anything about 3.11.1 specifically — this machine has 3.10.2, so whether 3.11 introduces
new breakage is untested. And the larger request from June 2024, linking libnormaliz into M2 so the
C++ engine can use it directly, appears not to have produced a pull request.
