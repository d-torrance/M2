Measured on 1.26.06-40-gd8e86d689d. Short answer: your intuition holds for `_`, and the other two
differences are below the noise.

Method — values checked equal first, then min-of-5 timings so the fastest run stands in for "no GC
happened here", run at 200000 elements twice and at 2000000 once:

```m2
L = toList(1..200000);
blah2 = (a,b) -> a+b;  pred = i -> i % 3 == 0;
foo = i -> i+1;        bar = i -> 2*i;        x = 7;
time' = f -> min apply(5, i -> first timing f());
```

Ratios are sugar ÷ lambda, so above 1 means the sugared form is slower:

| pair | 200k | 200k | 2M |
| --- | --- | --- | --- |
| `blah2_x` vs `y -> blah2(x,y)` | 1.21 | 1.09 | 1.29 |
| `not pred` vs `i -> not pred i` | 0.99 | 1.04 | 1.01 |
| `bar @@ foo` vs `i -> bar foo i` | 1.04 | 1.16 | 0.81 |

The subscript row is the only one that holds a direction — slower in every run I did, by something
like 10–30%. Negation is a wash. Composition changes sign, and I would not read the 0.81 as `@@`
being faster: at 2M each timing runs to seconds and garbage collection dominates. The honest summary
is that only `_` costs anything measurable.

Which matches the pseudocode you posted, and is worth spelling out because it says where the cost
is. In `apply(L, blah2_x)` the `2-OP _` node is evaluated **once**, before `apply` runs, and what
`apply` then calls per element is the closure it returned — so each element pays for one extra
function-call layer compared with `y -> blah2(x, y)`, whose body calls `blah2` directly. That
predicts a small constant overhead per element rather than anything scaling, which is what the
numbers show.

So there is no interpreter optimization being missed in the `not` and `@@` cases — there is nothing
there to recover. For `_`, the overhead is one call layer, and it is real but small enough that I
would choose between these two forms on readability rather than on speed.
