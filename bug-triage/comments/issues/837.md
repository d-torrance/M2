### Still there, and homogeneity is not the obstacle

```m2
i1 : R = ZZ[i]/(i^2+1); I = ideal"5,i+2";

i3 : minimalPresentation I

o3 = ideal (5, 5)

o3 : Ideal of ZZ[]
```

and with @mahrud's homogeneous variant, `ZZ[i, DegreeRank => 0]/(i^2+1)`, `isHomogeneous I` is
`true` and the answer is still `ideal (5, 5)`. So the 2018 guess that "minimality computations
succeed only in homogeneous situations" is not what is happening here.

Worth being exact about the severity: `ideal (5, 5)` and `ideal 5` are the same ideal, so nothing
is *wrong* — the result is redundant, not incorrect. `mingens` and `trim` both return
`5, i+2` unchanged, which is also a correct generating set and also not minimal.

### There is a PID strategy; this ring does not reach it

`M2/Macaulay2/m2/matrix2.m2:301` registers exactly the `smithNormalForm` approach from the reply
above:

```m2
addHook((trim, Module), Strategy => "PID",
    (opts, M) -> (
	R := ring M;
	if instance(R,PolynomialRing) and numgens R === 1 and isField coefficientRing R and not isHomogeneous M then trimPID M
	)
    )
```

`ZZ[i]/(i^2+1)` fails that guard twice over. It is a `QuotientRing` rather than a
`PolynomialRing`, and its coefficient ring is `ZZ` rather than a field. So the operative notion
of "PID" here is "univariate polynomial ring over a field" — narrower than the mathematical one,
and narrower than the title of this issue assumes. The Gaussian integers are a PID; M2 just has
no route to treating them as one.

That seems the most useful thing to record: the gap is a guard, not a missing algorithm, and
`trimPID` immediately above it is already written in terms of `smithNormalForm` and a change of
basis.
