Confirmed on 1.26.06, and the disagreement is a shortcut in `isVeryAmple` that is being applied
outside the case where it is valid.

`compute#Polyhedron#computedVeryAmple` tests each vertex in turn
([`Polyhedra/extended/polyhedron/properties.m2:32-34`](https://github.com/Macaulay2/M2/blob/6f6875e7b64318bb7d9558d585e68e40b3e39e68/M2/Macaulay2/packages/Polyhedra/extended/polyhedron/properties.m2#L32-L34)).
It collects the primitive outgoing edge directions, takes the product of the elementary divisors
of their Smith normal form, and if that product is 1 it accepts the vertex immediately:

```m2
ind := (smithNormalForm matrix {outgoingEdges})_0;
ind = product toList apply(rank ind, i-> ind_(i,i));
ind == 1 or (
```

That is sound at a **simple** vertex — one with exactly `dim P` edges — where the edge directions
are a basis of the tangent cone, so `ind == 1` means the cone is unimodular and there is nothing
left to check. At a vertex with more edges than that, the directions can generate `ZZ^n` as a
*lattice* while the cone they generate is not smooth, and the test proves nothing.

Your `P` is exactly that case. Instrumenting the loop over its six vertices:

```
vertex (0,0,0)  #edges 3  ind 1
vertex (1,0,0)  #edges 5  ind 1      <-- ambient dimension is 3
vertex (0,1,0)  #edges 4  ind 1
vertex (0,0,1)  #edges 5  ind 1
vertex (1,1,1)  #edges 3  ind 1
vertex (2,3,1)  #edges 4  ind 1
```

Every vertex takes the shortcut, so the two tests underneath it never run — and at `(1,0,0)`,
the vertex your `coneGens` are taken from, **both of them return false**. Running them by hand
there: the subset-sum test is false, and the Hilbert basis of the tangent cone comes back as

```
{(-1,0,0), (-1,0,1), (-1,1,0), (0,1,1), (0,2,1), (1,3,1)}
```

which is the basis you computed. Testing each element for membership in `P - (1,0,0)`, five of
the six pass and `(0,2,1)` is the single one that fails — the vector you named. So the code
already holds the evidence that `P` is not very ample, and discards it before looking.

Gating the shortcut on the vertex being simple:

```m2
(#outgoingEdges == dim P and ind == 1) or (
```

returns `false` for your `P` and still returns `true` for the unit simplex. I have not checked
what it costs on the package's own test suite, so that is a diagnosis rather than a proposed
patch.

The shortcut has been there since `isVeryAmple` was added — `2c4338389d`, René Birkner,
2010-01-10 — and has not been touched since, so this is not a regression.

`NormalToricVarieties` is a different implementation with a different open bug, #3575.
