Closing as not planned, from a sweep of the open issues — the premise turns out to run
against the project's own guidance.

Nothing has changed on the mechanics: there is still no shortcut for a string key, so
`x#"foo"` is written with the quotes, and `x.bar` remains sugar for `x#(global bar)`.

### Why the gap is not a problem to solve

The reasoning here is that a programmer "usually intends" a string key, because
`global k` may resolve differently later — so the shorter syntax attaches to the form you
want less often. The
[Package Writing Style Guide](https://github.com/Macaulay2/M2/wiki/Package-Writing-Style-Guide)
takes the other view:

> For keys in hash tables, use existing symbols, when possible. Examples: `source` and
> `target`, as keys for the source and target of a map

So symbol keys are the recommended form, and `x.source` is sugar for the thing a package is
being told to write. The convenience and the guidance point the same way rather than
opposite ways.

That qualifier — *existing* symbols — also disposes of the objection raised in this thread:

> Another disadvantage of `x.k` is that then the symbol `k` gets created and shows up in the
> dictionary, leading to complaints about the lack of documentation for it.

That cost only arises when `k` is a *new* symbol. Using `source`, `target` or another symbol
that already exists creates nothing and pollutes nothing, which is exactly what the style
guide asks for.

### What remains

String keys are still the right choice where no suitable symbol exists, or where the key is
genuinely data rather than a name — and there `x#"foo"` works, costs two quote characters,
and has no correctness problem. New syntax to save those two characters would mean a parser
change, which is a large lever for a small gain, and in nine years nobody has proposed a
concrete spelling for it.

Closing on that basis rather than on the merits of the observation, which was a fair one to
make. Thanks, @jakobkroeker.
