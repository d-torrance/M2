This looks fixed, by @jkyang92's own PR — [#4086](https://github.com/Macaulay2/M2/pull/4086),
*"Improve thread safety of value and readeval"*, opened the day after his comment above and
merged on 2026-05-14. Its description says so directly:

> This makes several variables thread local so that `value` and `readeval` in `interp.dd` is
> more thread safe. This seems to fix #3927.

The issue stayed open only because the PR was never linked to it, so nothing closed it
automatically.

Checked on 1.26.06 that the merge commit is actually in this build, and re-ran the reproducer
from the body — a race needs repetition rather than one run:

```m2
R = QQ[x];
taskResult \ apply(5, i -> schedule(() -> value "x"))
```

40 trials of 5 tasks, then 30 trials of 12, so 560 concurrent `value` calls: no `null` results
and no `mutable unexported unset symbol(s)` error.

Two caveats worth keeping attached, rather than letting the close swallow them:

- **Nobody is claiming the race is proven gone.** @jkyang92 wrote that making these thread local
  "makes this error at least unreliable enough so that I can't trigger it", and the PR says
  "seems to fix". 560 clean trials is evidence, not proof.
- **The PR flagged four more variables it deliberately did not change** — `previousLineNumber`,
  `interpreterDepth`, `errorDepth` and `current` (`loadDepth` is already thread local). Those
  are listed as worth investigating rather than as known bugs, but they should not disappear
  along with this issue.

Please reopen if it resurfaces.
