Part of this landed and part is still live, so here is the state on 1.26.06.

**Fixed.** The complaint from 2023-03-03 that locating anything exported by a package returned
nothing — @pzinn's own patch for it went in as 1eb0011ded (2024-07-17, *"fixed locate for symbols
declared by export"*), and `binding.d` now carries the line he proposed here:

```
if entry.position == tempPosition then entry.position = t.position;
```

So `locate symbol resultant` gives `Elimination.m2:123` and `locate symbol html` gives
`methods.m2:713`.

**Still live.** `methodOptions html` is `null` — the one pzinn said should work no matter what — and
`locate html` is `null`. `code html` no longer returns nothing, but what it returns is
`method function with a single argument, html: source code not available`, which is a message rather
than an answer.

**Untouched, and probably the real ask.** Neither `locate` nor `code` points at the
`html = method(...)` line. On every method function I tried, across both classes in the title:

```
locate det          option.m2:15:14-18:8      (MethodFunctionWithOptions)
locate hooks        option.m2:15:14-18:8      (MethodFunctionSingle)
locate resultant    option.m2:15:14-18:8
```

all of them the generic wrapper — @mahrud's "kludge", and the same thing as #2569. And
`methodOptions hooks` is null too, even though `hooks` is the `MethodFunctionSingle` this issue is
titled for.

pzinn's last suggestion, from 2023-04-28 — that the `methopts` argument trick which lets
`MultipleArgsWithOptions` recover its options through `frame` could be applied to
