Closing as a duplicate of #936, which reports the same defect from the other side and is where the
design discussion has been happening.

The mechanism is the one @mahrud named in the first reply here. `pdim` returns the length of a free
resolution, and that length is the projective dimension only when the resolution is minimal — which
M2 guarantees for graded modules over graded rings and not otherwise. So for inhomogeneous input the
answer depends on the presentation, which is what this issue shows (`imA == imB` is `true`, `pdim`
gives 1 and 0), and it can also be too large by exactly the amount that breaks a short exact
sequence, which is what #936 shows:

```
i1 : R = QQ[x,y];
i2 : I = ideal((x^3 + y)^2, (x^2 + y^2)^2, (x + y^3)^2, (x*y)^2);
i3 : pdim (module I)     o3 = 2
i4 : pdim (R^1 / I)      o4 = 2
```

Both are still current on 1.26.06.

The two threads have also converged on the same remedies — @kschwede's `projDim` in `FastMinors`,
and either an error or a warning for inhomogeneous input — so they are better read together.
#936 additionally carries @mikestillman's April 2026 note that `pdim` over a quotient ring uses the
default `LengthLimit`, and @mahrud's suggestion to push forward to the ambient polynomial ring.

#3656 is a separate request and is not affected by this.
