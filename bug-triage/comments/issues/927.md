`lookup(basis, ZZ, ZZ, LieAlgebra)` is `null` — nothing was installed and nothing was said.

The error this issue asks for is already written. It just does not survive the `TYPE => function`
form of the assignment. Compare:

```
i2 : basis(ZZ,ZZ,LieAlgebra) := (x) -> opts -> {}
stdio:2:24:(3): error: expected method for ternary operator to be a function of 3 variables

i2 : basis(ZZ,ZZ,LieAlgebra) := List => (x) -> opts -> {}
o2 = List => FunctionClosure[stdio:2:35-2:52]
```

Same wrong function, same arity check, and the second one reports success.

`installIt` in `M2/Macaulay2/d/hashtables.dd` is where it goes. An `Option` on the right-hand side
takes the `optionClass` branch, which calls `installIt` recursively for the function, **drops the
value it returns**, records the typical value, and returns `value`:

```
is x:List do (
     if x.Class == optionClass && length(x.v) == 2 then (
	  installIt(numtypes,assgnmt,h,key,x.v.1);
	  storeInHashTable(typicalValues,
	       if numtypes == 1 then Expr(Sequence(key,Expr(h))) else key,
	       x.v.0);
	  value)
```

The recursive call is the one that builds `"expected method for ternary operator to be a function of
3 variables"`, and in this language an error is a returned packet, so dropping the value drops the
error. Visible from the outside — the typical value gets recorded for a method that does not exist:

```
i3 : debug Core
i4 : typicalValues#(basis,ZZ,ZZ,LieAlgebra) === List     o4 = true
i5 : lookup(basis,ZZ,ZZ,LieAlgebra) === null             o5 = true
```

So this looks like propagating the recursive result rather than adding a new check. The nullary
`installMethod` a few lines below has the same shape, calling `installMethod(meth,x.v.1)` and
discarding it, and would want the same treatment.
