Some findings on this, from reproducing it deliberately rather than by accident.

### Reproducing it without editing anything

```sh
CPPFLAGS="$(pkg-config --cflags blas)" CBLAS_LIBS="$(pkg-config --libs blas)"
```

On Debian with `intel-mkl` installed, the alternatives-managed `blas.pc` supplies
`-I/usr/include/mkl -m64` and `-lmkl_rt -lpthread -lm -ldl`. Setting `CBLAS_LIBS` is the operative
part — see the last section for why.

### What actually collides — and it is not the complex type

The first error is not on `zgetrf_`:

```
lapack.hpp:22:5: error: conflicting declaration of C function
                 'int dgesv_(int*, int*, double*, int*, int*, double*, int*, int*)'
mkl_lapack.h:14479:6: note: previous declaration
                 'void dgesv_(const int*, const int*, double*, const int*, int*, double*, const int*, int*)'
```

`double* a` matches on both sides, and under LP64 `MKL_INT` *is* `int`. The conflict is the **return
type** (`int` vs `void`) and the **`const` qualifiers**.

That generalises: `e/basic-mutable-matrices/lapack.hpp` declares 20 prototypes, **19 of which return
`int`**, and only one uses `const`. MKL declares all of them `void` with `const` inputs. So 19
collide, and `dgesv_` is simply the first one in the file.

This is probably why the `#define MKL_Complex16 double` workaround felt sketchy — it addresses the
complex-pointer mismatch, which is real but is the minority case, and leaves the return-type and
`const` conflicts on the other routines untouched.

### There is a precedent for the fix, in the same file

The one prototype that *doesn't* collide is `dgetrf_`, declared `void` with `const` inputs. It looks
that way because of `55c1224458` (Jakob Kröker, 2014-01-17), *"using identical interface to dgetrf_
in lapach.h and in config-blas.h"* — the same collision, twelve years ago.

Without MKL, `fflas-ffpack/config-blas.h` declares exactly one LAPACK routine of its own:

```c
void dgetrf_ (const CBLAS_INT *, const CBLAS_INT *, double *, const CBLAS_INT *, CBLAS_INT *, CBLAS_INT *);
```

So in 2014 there was one conflict and it was fixed by matching the signature. With
`__FFLASFFPACK_HAVE_MKL`, `config-blas.h` swaps that single declaration for `#include <mkl.h>`, which
declares the whole set — hence the other 19.

That suggests two shapes for a fix: match signatures as was done in 2014, now nineteen times; or
guard the block with `#ifndef __FFLASFFPACK_HAVE_MKL` and let MKL's declarations stand, since
`config-blas.h` is already in scope wherever this collides.

### Why cmake hits this and autotools does not

`CBLAS_LIBS` is a legacy fflas-ffpack variable that was renamed to `BLAS_LIBS`.
[linbox-team/fflas-ffpack#226](https://github.com/linbox-team/fflas-ffpack/pull/226) fixed one of the
two stale references in 2019; `macros/mkl-check.m4` is the other, and still reads

```m4
MKL_USED=`echo $CBLAS_LIBS | grep -i MKL`
```

Nothing in fflas-ffpack sets `CBLAS_LIBS`, and it is not a declared precious variable — so the MKL
check has been unreachable through the documented `--with-blas-libs` for seven years.

M2's cmake build sets it explicitly (`cmake/build-libraries.cmake:624`, with the comment
`# see macros/mkl-check.m4`), which is the only occurrence of `CBLAS_LIBS` in M2 — that line is what
makes cmake builds define `HAVE_MKL`. The autotools build passes `--with-blas-libs="@LINALGLIBS@
@FCLIBS@"`, which sets `BLAS_LIBS` and never trips the grep.

**So autotools builds against MKL currently work only because of that upstream typo.** If
`mkl-check.m4` is ever corrected to read `BLAS_LIBS`, every autotools build with MKL in `LINALGLIBS`
will define `HAVE_MKL` — and fail at fflas-ffpack's own configure first, since neither build system
passes BLAS-specific include flags and Debian keeps `mkl.h` in a subdirectory that is not on the
default search path. (cmake passes only generic `CPPFLAGS`/`CFLAGS`; the original report found the
header because oneAPI's `setvars.sh` had put MKL on `CPATH`.)

Worth noting for whichever way this goes: M2 includes only `ffpack/ffpack.h`,
`field/modular-balanced.h` and `field/modular-positive.h`, so none of the MKL sparse-BLAS paths that
`__FFLASFFPACK_HAVE_MKL` gates are reachable from M2. The macro mostly swaps declarations for calls
that reach the same library either way — which is an argument for not defining it at all, with the
caveat that under ILP64 `MKL_INT` is 64-bit and the declarations would then genuinely differ.
