This reproduces here, so to answer @mikestillman's question about OS and architecture with a third
data point: **Linux x86-64, Ubuntu 24.04, 12 cores, M2 1.26.06-40-gd8e86d689d** — @mahrud's
reproducer segfaults in **9 of 54 runs**, about one in six. The snippet doesn't set
`allowableThreads`, so that is the default 5 with 10 tasks.

Making it work harder does *not* help: 3000 concurrent `poincare` calls on `QQ[x_1..x_10]` at 13
threads, across three processes, ran clean. Whatever the race is, it is not simply a matter of more
contention.

### Two things that make this hard to chase, both worth knowing before you try

**The exit status doesn't tell you.** `segv_handler` ends in `_exit(1)`, but I never saw 1 — the
runs that crashed exited **0** or **2**. My first pass over 25 runs recorded every one as clean on
exit codes while three of them had in fact crashed. Grep stderr for `SIGSEGV` instead.

**The crash handler faults inside itself, so there is no trace to compare.** Every crash log here
stops after two lines, with no frames and no `-- end stack trace *-`, and two of the six went
further:

```
-- SIGSEGV
-* stack trace, pid: 3911957
-- SIGSEGV
-- SIGSEGV handler called a second time, aborting
```

That is
[`segv_handler`](https://github.com/Macaulay2/M2/blob/1cbd50ef91019a527d4cba7b3b9796200c3bfb55/M2/Macaulay2/bin/main.cpp#L233-L245)
segfaulting while evaluating `boost::stacktrace::stacktrace()` and tripping its own re-entry guard.

This is not a missing-symbols problem: `macaulay2-dbgsym` is installed at the matching version and
the 52 MB debug file matches `M2-binary`'s build-id, so the symbols are right there. I have not
established *why* `stacktrace()` faults — symbolising that much separate debug info allocates, and
allocating in a signal handler after a heap-corrupting crash is a plausible way to die, but that is
a guess and not a measurement.

One detail that does look like a defect on its own: the guard is `static int level`, a plain `int`,
and in another log the `-* stack trace, pid:` line printed *after* the abort message — that is two
threads inside the handler at once rather than one thread re-entering, which `level > 1` cannot
distinguish. For a crash that only appears under `schedule`, that is precisely the case it meets.
