@mikestillman's diagnosis above is right in outline: *"starting a GB without using Hilbert
function information, and then continuing the GB computation using Hilbert function
information."* It turns out not to be sufficient, though, and the part it is missing narrows the
search a good deal.

### A stopped-and-resumed GB is not enough; it has to be the `mingens` stop

All three of these leave a Gröbner basis in the same cache slot on `gens I` —
`GroebnerBasisOptions{Syzygies => false, SyzygyRows => 0, HardDegreeLimit => null}` — and then
have the `poincare` hint attached before anything asks for the GB again:

| run before the hint | GB state when the hint arrives | state after `dim I` | `dim I` |
| --- | --- | --- | --- |
| `trim` | `StopWithMinimalGenerators; all S-pairs handled up to degree 1` | `done; S-pairs encountered up to degree 1` | **10** |
| `gb(presentation M, DegreeLimit => 2)` | `DegreeLimit; all S-pairs handled up to degree 2` | `done; S-pairs encountered up to degree 3` | 9 |
| nothing | — | `done; S-pairs encountered up to degree 3` | 9 |

The middle row is the one that matters. It is a genuinely incomplete GB, stopped below the
degree where `cde` appears, resumed under the hint in the same cache slot — and it goes on to
degree 3 and gets the right answer. So resuming a stopped computation under a hint is fine in
general; what is not fine is resuming one stopped by `StopWithMinimalGenerators`, which is the
stop `mingens` uses (`M2/Macaulay2/m2/matrix2.m2:198`):

```m2
mingb := m -> gb (m, StopWithMinimalGenerators=>true, Syzygies=>false, ChangeMatrix=>false);
```

and which is therefore what `trim` leaves behind. That is also why removing the `trim` makes the
problem go away, as noted above — without it there is no such stopped computation to resume.

### It is the cached computation, not the input

Two controls, identical except for whether the cached GB comes along:

```m2
-- same entries, different matrix object
g = matrix entries gens I;  M = cokernel g;  ... hint ...  dim M   -->  9,  correct

-- same matrix object
J = ideal gens I;                            ... hint ...  dim J   --> 10,  wrong
```

The second is wrong because `(gens I).cache.cokernel` hands back the very module that is
carrying the `poincare` hint, so the stale computation and the hint meet on the same object. And
reordering the generators by hand into the order `trim` produces, without calling `trim`, gives
9 — so it is not the generating set either.

### Where it stops early

With the hint in play, `hf_diff` is the difference between the Hilbert numerator of the lead
terms found so far and the numerator that was supplied, and at each new degree
`e/groebner-computations/gb-default.cpp:2497` does

```cpp
if (hilb_n_in_degree == 0) flush_pairs();
```

which is how a hint lets the computation finish early. Coming out of the min-gens stop the
existing lead terms are `ae, ab`, and that comparison evidently reaches zero at degree 1 rather
than at 3, so the S-pairs that would have produced `cde` are flushed and the basis is declared
done. The three-row table says the state carried out of `StopWithMinimalGenerators` is what
makes that comparison wrong, rather than the resumption as such.

failure is narrower than it looked: a Hilbert hint set on a module whose generator matrix has
already been through `mingens` (directly, or via `trim`).
