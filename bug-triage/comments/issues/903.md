Closing this. The battle it records was over before the issue was a day old, and the tree has
been stable ever since.

`4319f1ea80`, the second of the two commits quoted above, was reverted the same day:

```
4319f1ea80  2018-12-27  make some include directories into system include directories
ae31230c3a  2018-12-27  undo a change
```

`M2/include/config.Makefile.in` has used plain `-I` for all three include directories from then
until now —

```make
	-I@abs_top_srcdir@/include						\
	-I@abs_top_builddir@/include						\
	-I$(BUILTLIBPATH)/include						\
```

— with no `-isystem` in the file at all. It has been edited a number of times since (2021, 2024,
2025 and twice in 2026) and nobody has revisited the flag.

Meanwhile `-isystem` is still used, three times, in `M2/configure.ac`, and every one of them is
for a **third-party** include directory. That split looks less like an unresolved conflict than
like the answer to it: `-I` for our own headers, where the point is that they take precedence
over anything the system provides, and `-isystem` for external ones, where the point is to
suppress their warnings and keep them out of our dependency graph.

### Closing over an earlier "no"

@DanGrayson declined @mahrud's offer to close this in June 2020, saying *"at some point I'd like
to rethink all that"* — and that was two years after the revert, so it was a considered decision
with the code already in its current state, not an oversight. Closing it anyway, six years
further on, because a standing wish to revisit a design is not something this issue can track:
it has no criterion for being done, and the concrete conflict it was opened to record no longer
exists. If the include-path arrangement does get rethought, a fresh issue stating what should
change would start from a much better place than these two commit messages.
