Still open, but two of the three boxes above are done and the checklist has never been updated to
say so — so the issue reads as untouched when it is a third of the way from the other end.

### `nullptr, not 0 as a pointer, or NULL either`

Done, and it took two attempts. @moorewf ran clang-tidy over `e/` in
[#2886](https://github.com/Macaulay2/M2/pull/2886) (2023-06-21); it was reverted six weeks later
by [#2925](https://github.com/Macaulay2/M2/pull/2925), not because it was wrong but because it
fought the `feature/monoids` branch — *"we will rerun the clang-tidy code that created 2886 later,
after that code is merged in"*. @mahrud did exactly that in
[#3092](https://github.com/Macaulay2/M2/pull/3092) (2024-01-26). `e/` now has 3004 `nullptr`
against 158 remaining `NULL`.

### `remove the array<T> and queue<T> classes in the e directory`

Done. `array<T>` became `VECTOR(T)` in [#1461](https://github.com/Macaulay2/M2/pull/1461)
(2020-06-28) and `e/array.hpp` went with it; `e/queue.hpp` was deleted in `0b0804ae7b`
(2021-06-30).

### `change pointer types to e.g. unique_ptr`

This is the one that has not moved. `e/` currently holds 93 mentions of `unique_ptr`,
`shared_ptr`, `make_unique` or `make_shared` against 808 raw `new T` sites and 312 uses of the
`newitem` / `newarray` macros — so ownership is still expressed the 1997 way almost everywhere.
It is also the box that overlaps #983, which is about the allocation side of the same question.

### Two things from the discussion above that did happen

@rz10x suggested C++17. The engine moved to it on 2021-01-20 (`41d487cc17`, *"change d and e
compilation to c++17"*), went to C++20 in `54f2e64b0b` (2023-07-29) and came back to C++17 in
`4f19e75ce8` (2024-01-24) — `e/Makefile.in:17` and `CMakeLists.txt:23` are the two places that
say so.

@mahrud wrote that concepts were worth starting on and that *"perhaps lines could be commented out
for now"*. That is precisely where it stands: `e/gb-f4/PolynomialList.hpp:260` reads

```cpp
// TODO: once we go to c++20, enable the concept PolynomialStream
```

and the concept itself is written out but parked in `e/unused/PolynomialStream.hpp`.

@rz10x's 2019 list ended with *"Let me know what you think!"* and never got a direct answer. The
honest six-year answer is a mixed one: the C++17 suggestion was taken, but most of the rest of that
list is where it was. `#if 0` blocks in `e/` have gone from 192 to 185, `ERROR(...)` is still used
885 times rather than C++ exceptions, and `.clang-format` was already in the tree when the
suggestion was made. The `unique_ptr` box above is the one with the most behind it.
