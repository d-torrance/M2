Confirmed — the figure is two decades out of date. `Macaulay2Doc/ov_files.m2:408` still says the
pipes "typically hold only 4096 bytes", but on 1.26.06 through `openInOut "!cat"`, 65000 bytes go in
and come back in a single round trip with no blocking. Linux's default pipe capacity has been 65536
bytes since kernel 2.6.11 (2005), and on this machine `/proc/sys/fs/pipe-max-size` is 1048576.

The general warning is still right — write more than the pipe holds without reading and you
deadlock. Only the number is wrong.

**`F_SETPIPE_SZ` is the mechanism for the actual ask.** Per `fcntl(2)`, available since Linux 2.6.35:
an unprivileged process may raise a pipe's capacity to anything between the page size and
`/proc/sys/fs/pipe-max-size`, returning the capacity actually set (rounded up to a power-of-two page
multiple); going above that limit gives `EPERM` unless the process has `CAP_SYS_RESOURCE`. The
catch for us is that it is **Linux-specific** — there is no macOS equivalent — so it can raise the
ceiling where it exists but cannot be the portable answer that `openInOut`'s documentation needs.

One thing the documentation doesn't mention at all, which is what a caller actually trips over:
**`read` may return short.** Asking for 8000 bytes back returned 4096; asking for 100000 returned
61248. That is ordinary behaviour for a pipe, but nothing in the `openInOut` documentation says a
single `read` can return fewer bytes than requested, so code written on that assumption loses data
silently rather than blocking. Arguably that is the more useful thing to document than the exact
capacity, since it stays true whatever the buffer size is.
