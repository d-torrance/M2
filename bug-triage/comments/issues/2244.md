Closing this as not planned. Mixing ABI-incompatible builds of the same library is unsupported, so a
crash in a static destructor at process exit is the expected consequence rather than a defect in
Macaulay2 — which answers the question this report ends on. The Debian transition it was blocking
(bug #995020) completed years ago, and both NTL versions involved are long gone.

Worth noting what the absence of a reproduction here does and does not show: on a machine with a
consistent NTL — 11.4.3 throughout — `GF 8` followed by `exit` is clean. That is the trigger being
absent, not the bug being fixed. Anyone who builds M2 and flint against different NTL releases should
expect the same thing.

The trace, for whoever meets this shape again:

```
3# NTL::UniqueArray<NTL::UniquePtr<NTL::FFTPrimeInfo, NTL::DefaultDeleterPolicy> >::~UniqueArray()
     at ../include/NTL/SmartPtr.h:1593
4# __cxa_finalize
5# /usr/lib/x86_64-linux-gnu/libntl.so.43
```

A static destructor in one build of NTL running against state created by another. The tell is that it
happens at exit, after all useful work — so if it ever appears with matched libraries, that would be
a real bug and worth a fresh issue rather than reopening this one.
