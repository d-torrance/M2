Closing: fixed by #4248, *"fix for lifting matrices over QQ"* (merged 2026-05-04), commit
`6e6980bc6b`. All four assertions above pass on 1.26.06, and so does the `ZZ/32003` control.

Confirmed on the commit itself rather than inferred: building the engine with and without that
commit's hunk, and changing nothing else, gives

```
with the hunk:      div1*f - elem  =  0
hunk reverted:      div1*f - elem  =  192*y^3*x^12+3840*y^6*x^7+768*y^4*x^8+129792*y^2*x^9
                                      +22272*x^10+2595840*y^5*x^4+964608*y^3*x^5+89088*y*x^6
```

and that residual is byte-for-byte the one release-1.25.11 produces. Its coefficient gcd is
192 = 2<sup>6</sup>·3 with the quotient integral, so the quotient was off by a pure rational
constant while `elem % f` stayed correctly zero — which is what the fix addresses: in
`ReducedGB_Field::remainder`, `gbvector_normal_form` on the syzygy part can yield a denominator, and
the old code discarded it. That call goes through `get_quotient_info()`, so the denominator only
arises when there is a quotient ideal to reduce by, which is why this was a quotient-ring bug; and
over a finite field the stray factor is a unit and normalises away, which is why `ZZ/32003` was
always clean.

One thing worth flagging, @mikestillman: this defect was found **twice from the same source report**
and the two were never linked. This issue opens "uncovered while chasing down a bug in
integralClosure communicated by @Douglas-Leonard". #4235, filed sixteen months later, opens "I found
this starting with a bug report of @Douglas-Leonard for an example computing integral closures which
was getting a garbage result". #4235 got the diagnosis, the fix and the regression test
(`tests/normal/gbring-lift-bug.m2`); this one stayed open.

@Douglas-Leonard's correction above is right, incidentally — `elem = q*f + r`, and the remainder is
zero here, so the sign never affected the result.
