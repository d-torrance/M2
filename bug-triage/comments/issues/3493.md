Closing as `wontfix`. The half of this that was a real question got answered on the day it was
filed, and the half that remained turns out to have a definite answer.

**The dead code is gone.** 37f8527eff, *"deleted unusable binary ops `X.Y := f` and `X#Y := g`"*
(PR #3472, merged 2024-09-25) removed the chunk linked above. The `:=` path in `convertr.d` is now a
plain `convertMultaryInstallCode(InstallMethodFun, ...)` with no `SharpS`, `DotS` or `UnderscoreS`
special-casing at all. So "was this an incomplete feature?" — no; it was unreachable code, and it
has been deleted.

**And the rejection is deliberate rather than an oversight**, which is the part worth recording.
`binding.d:761-771` checks only `opHasBinaryMethod` for `:=`, but for `=` it carries an explicit
exemption naming both operators:

```
if !(binary.Operator.word == DotS.symbol.word
     || binary.Operator.word == SharpS.symbol.word
     || opHasBinaryMethod(binary.Operator.entry))
then makeErrorTree( assn.Operator, "can't assign a value for this binary operator");
```

`#` and `.` take *values*, not methods — `H#k = v` and `H.k = v` work and are meant to. Both sit in
`fixedBinaryOperators` alongside `:=`, `=`, `;`, `,` and `===`.

**For `#`, the reason is semantic and it is the stronger of the two.** Most M2 objects are hash
tables or basic lists underneath, and `#` is how you reach that representation. Of the 160 types
reachable from `dictionaryPath`, **113 already give `#` a meaning** — 60 descending from `HashTable`,
53 from `BasicList` — and of the 47 that descend from neither, seven more are covered anyway
(`String`, `Net`, `NetFile`, `Database` and the three `Dictionary` types: exactly the list M2's own
error message enumerates). What is left unclaimed is numbers, functions, `Symbol`, `Boolean`,
`Keyword`, `Task`, `Mutex` — nothing anyone wants to subscript. Meanwhile 423 lines in `m2/` and
6059 across `packages/` read a representation by name through `X#"..."`.

The example at the top of this issue makes the point by itself:

```m2
i1 : T = new Type of MutableHashTable;

i2 : # T

o2 = 0
```

`#T` is already defined, because a `Type` *is* a hash table. So the request is not "give `#` a
meaning here" but "let a package replace the meaning `#` already has", on objects whose hash tables
Core reads by name in thousands of places. #3480 and #2847 are open bugs that exist *because* of
that reach — `#(mingens I)` returns 5 for every matrix — which is a fair illustration of how much is
resting on it.

**For `.`, the reason is narrower.** `binding.d:759` binds the right-hand side of `.` in the
`globalDictionary`, and `:775` requires *"expected a symbol to right of `.`"*, so a method on `.`
would receive a symbol rather than a value. `Python.m2:192` already does the only thing such a
method could:

```m2
PythonObject @@  Thing := (x, y) -> pythonObjectGetAttrString(x, toString y)
```

so overloading `.` would buy nicer syntax, not new capability.

One loose end, since it outlives this issue: 11ffa9596f, the sibling commit in the same PR, left
`-- TODO: can #T be implemented here?` beside the `Unary` case of the `ColonEqual` branch in
`convertr.d`. With this closed, the tree is still asking a question the tracker has answered, and
that comment should probably go.
